# ADR-T2-03: Обработка потоков в реальном времени

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, Pricing team, Driver team, data-инженеры

## Контекст

Два бизнес-требования платформы GoFuture требуют вычислений над потоками
событий в реальном времени, а не только хранения фактов: динамическое
ценообразование и "умное" перераспределение водителей (борьба с "горячими
зонами", вместо назначения просто ближайшего водителя, см.
[docs/context.md](../docs/context.md)). Оба сценария опираются на события
`DriverLocationUpdated` и `BookingCreated` (см.
[01-domain-events.md](01-domain-events.md)) и производят `SurgeActivated`
и решения по матчингу для Driver Service. Кроме этих сложных сценариев,
часть сервисов нуждается только в простых потоковых операциях — проекциях и
обогащении событий данными из локального состояния сервиса (например,
подстановка шаблона в `NotificationRequested`).

Нужно выбрать инструмент(ы) обработки потоков и явно разграничить, какой
инструмент применяется для каких сценариев.

## Требования

- Оконные агрегации спроса/предложения по географическим ячейкам (`geo_cell`)
  в масштабе всей платформы (500 тыс. конкурентных поездок, требование П1,
  [Task1/01-nfr.md](../Task1/01-nfr.md)), с низкой задержкой пересчёта.
- Устойчивость к опоздавшим событиям (`DriverLocationUpdated` с мобильных
  сетей может приходить с задержкой) — необходима обработка по времени
  события (event-time), а не только по времени обработки.
- Корректность вычислений, влияющих на деньги: `SurgeActivated` напрямую
  используется `Pricing Service` при расчёте `PriceCalculated`, что в свою
  очередь определяет сумму `PaymentAuthorized` (требование С2/С3,
  [Task1/01-nfr.md](../Task1/01-nfr.md)) — обработка не должна приводить к
  повторному учёту одного и того же события в агрегате.
- Простые проекции и обогащение (без сложных окон/CEP) не должны требовать
  отдельного тяжёлого кластера обработки потоков для каждого случая —
  иначе эксплуатационные расходы растут без соразмерной выгоды.
- Инструменты должны по возможности переиспользовать существующий стек
  (в контексте компании уже используются Spark/Flink для аналитики, см.
  [docs/context.md](../docs/context.md)), а не добавлять принципиально
  новый класс технологий без необходимости.

## Решение

### Flink — для сложных сценариев реального времени

**Динамическое ценообразование (surge)**: Flink-джобы читают
`sea.driver.location.updated` и `sea.booking.created` (см.
[02-kafka-topics.md](02-kafka-topics.md)), выполняют оконную агрегацию
(скользящие/тумблинговые окна по `geo_cell` и времени) для расчёта
соотношения спроса и предложения, и публикуют `SurgeActivated` при
превышении порога. Pricing Service потребляет `SurgeActivated` как входной
сигнал для `PriceCalculated`.

**"Умное" перераспределение водителей**: отдельный Flink-джоб объединяет
несколько потоков (`DriverLocationUpdated`, `SurgeActivated`,
`BookingCreated`) для принятия решения не о "ближайшем", а о наиболее
подходящем водителе с учётом текущей и прогнозируемой нагрузки зоны — join
нескольких потоков и паттерн-детекция (например, "водитель простаивает в
зоне с избытком предложения — направить сигнал в сторону дефицитной
соседней зоны") лучше выражаются через богатую модель состояния и CEP,
доступную во Flink, чем через простые точечные трансформации.

**Обоснование выбора Flink для этих двух сценариев**:

- Настоящий потоковый (не микро-batch) движок — минимальная задержка
  между поступлением событий и пересчётом surge/матчинга.
- Обработка по времени события (event-time) с watermarks — устойчивость к
  задержкам мобильной телеметрии без искусственного занижения точности
  агрегатов.
- Управление состоянием (state backend, например RocksDB) с exactly-once
  через распределённые чекпоинты — критично, так как результат
  (`SurgeActivated`) напрямую влияет на денежную сумму дальше по цепочке
  (`PriceCalculated` → `PaymentAuthorized`); повторный учёт одного и того
  же события в оконном агрегате исказил бы цену.
- Flink уже присутствует в стеке компании для аналитики (см.
  [docs/context.md](../docs/context.md)) — переиспользование известного
  инструмента, а не добавление нового класса технологий ради двух
  сценариев.

### Kafka Streams — для простых потребителей

Используется там, где обработка ограничена одним сервисом и не требует
сложных оконных агрегаций или CEP:

- **Проекции**: например, материализация текущего облегчённого read-model
  статуса заказа для внутренних нужд сервиса на основе последовательности
  `Booking*`/`Ride*` событий одного и того же `booking_id` (простая
  KTable-агрегация "последнее известное состояние").
- **Обогащение**: например, Notification Service обогащает
  `NotificationRequested` данными шаблона из локальной KTable (таблица
  шаблонов, реплицируемая из `notification_templates`), не поднимая
  отдельный кластер обработки потоков ради этой операции.

**Обоснование выбора Kafka Streams для этих сценариев**: Kafka Streams —
библиотека, встраиваемая непосредственно в процесс сервиса, а не отдельный
кластер, как Flink. Для локальных, привязанных к одному домену
трансформаций это исключает лишний эксплуатационный компонент, естественно
масштабируется вместе с самим сервисом (автоскейлинг, требование М3,
[Task1/01-nfr.md](../Task1/01-nfr.md)) и не требует отдельной команды
для поддержки ещё одного распределённого кластера обработки потоков.

### Общее правило выбора

Flink — когда обработка агрегирует данные из нескольких топиков/доменов в
масштабе всей платформы или региона, требует оконной семантики по времени
события и/или влияет на денежные вычисления, требующие exactly-once. Kafka
Streams — когда обработка локальна для одного сервиса/домена, стейт
небольшой и укладывается в процесс сервиса, а разворачивать отдельный Flink
job было бы избыточно.

## Альтернативы

- **Spark Structured Streaming для всех сценариев реального времени.**
  Отклонено: микро-batch модель хуже подходит для latency-чувствительного
  surge-ценообразования и матчинга водителей, чем true streaming Flink.
  Spark уже используется в стеке для оффлайн/почти-реального-времени
  аналитики совместно с ClickHouse и DataLens (см.
  [docs/context.md](../docs/context.md)) — эта роль за ним и остаётся, без
  дублирования для задач с жёсткими требованиями к задержке.
- **Kafka Streams для surge-ценообразования и матчинга водителей.**
  Отклонено: реализация сложных оконных агрегаций по географическим
  ячейкам в масштабе платформы и CEP-логики "умного" перераспределения
  средствами Kafka Streams потребовала бы фактически заново реализовать
  значительную часть возможностей, доступных во Flink "из коробки"
  (продвинутые окна, event-time watermarks, checkpoint-based exactly-once
  для больших состояний) — риск изобретения велосипеда поверх более
  простого инструмента.
- **Flink для всех потребителей, включая простые проекции/обогащение.**
  Отклонено: избыточные операционные расходы (отдельный Flink job/кластер)
  для задач, решаемых лёгкой встроенной библиотекой; увеличивает число
  эксплуатируемых компонентов без выигрыша в возможностях.

## Компромиссы и риски

- Одновременное использование двух инструментов потоковой обработки (Flink
  и Kafka Streams) увеличивает разнообразие технологий, которые должна
  поддерживать платформенная команда/SRE — правило выбора (см. раздел
  "Общее правило выбора") должно соблюдаться дисциплинированно, иначе
  границы применения размоются.
- Flink с exactly-once чекпоинтами для больших stateful окон (потенциально
  миллионы активных водителей/поездок в самом крупном регионе) требует
  надёжного распределённого хранилища состояния — операционная сложность
  выше, чем у типовых stateless сервисов, и требует отдельного внимания
  SRE при эксплуатации.
- Настройка watermark-стратегии для устойчивости к задержкам мобильной
  телеметрии — компромисс между задержкой пересчёта surge и полнотой учёта
  поздних событий: слишком агрессивный watermark занижает спрос/предложение
  (теряет поздние события), слишком консервативный — увеличивает задержку
  реакции цены на изменение обстановки.
- Kafka Streams встроен в процесс сервиса — масштабирование
  потоковой обработки происходит вместе с масштабированием самого сервиса,
  что удобно, но не позволяет масштабировать обработку потока независимо
  от остальной бизнес-логики сервиса, если один из компонентов начнёт
  требовать существенно другого профиля ресурсов, чем остальной сервис.
