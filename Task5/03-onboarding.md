# ADR-T5-03: Автоматизированный онбординг партнёра

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда, SRE

## Контекст

Бизнес-цель — быстрый запуск партнёров в новых регионах. Модель изоляции
([01-tenancy-model.md](01-tenancy-model.md)) и IAM
([02-iam.md](02-iam.md)) определяют, ЧТО должно быть создано для нового
тенанта; этот документ определяет, КАК это создаётся — как
последовательность автоматизированных шагов от заявки партнёра до
активации, за целевое время 2–4 недели для стандартного (pool) партнёра.

## Требования

- Заявка партнёра должна инициировать процесс через API самообслуживания,
  без обязательного ручного проектирования инфраструктуры инженером на
  каждого нового партнёра.
- Каждый шаг должен быть воспроизводим (идемпотентен) и не зависеть от
  памяти конкретного инженера — Infrastructure as Code, а не runbook,
  выполняемый руками.
- Новый тенант не должен получать боевой трафик до прохождения
  smoke-тестов, подтверждающих изоляцию данных
  ([01-tenancy-model.md](01-tenancy-model.md)) и работоспособность
  сквозного сценария.
- Время онбординга 2–4 недели — целевое для pool и silo-схемы; для
  silo-уровня "выделенный региональный стек"
  ([01-tenancy-model.md](01-tenancy-model.md)) целевое время явно другое
  (см. риски) — нельзя обещать единый срок для всех уровней изоляции.

## Решение

### Оркестрация: Onboarding Service

Процесс координирует **Onboarding Service** — платформенный сервис,
играющий для процесса онбординга ту же роль, что Booking Service играет
для саги поездки ([Task2/04-saga.md](../Task2/04-saga.md)): хранит
состояние прогресса (какие шаги пройдены для конкретной заявки),
инициирует следующий шаг, обрабатывает отказ шага. Тот же архитектурный
паттерн (оркестрация вместо хореографии), выбранный ранее по тем же
причинам — наблюдаемость состояния каждой заявки и предсказуемая
компенсация при отказе шага, а не переоткрытие вопроса заново.

### Автоматизация: Terraform + Kubernetes operator

- **Terraform** — декларативное, одноразовое на этапе онбординга
  провижининг ресурсов, для которых достаточно один раз применить
  описание состояния: realm и клиенты Keycloak, топики/ACL Kafka, объекты
  квот/rate-limit API Gateway, дашборды и datasource Grafana.
- **Kubernetes operator** (кастомный `Tenant` CRD и контроллер) —
  постоянное согласование фактического состояния тенанта с желаемым:
  обрабатывает изменения уровня изоляции post-factum ([01-tenancy-model.md](01-tenancy-model.md)),
  масштабирование квот, деактивацию/оффбординг, обнаружение расхождения
  (drift) между тем, что задеклара Terraform, и тем, что реально
  развёрнуто. Onboarding Service создаёт объект `Tenant` в кластере;
  дальнейшую жизнь тенанта (не только первичное создание) ведёт
  reconciliation-цикл оператора, в т. ч. повторно вызывая нужные
  Terraform-модули при расхождении.

### Последовательность шагов

1. **Заявка через API самообслуживания.** Партнёр (или бизнес-девелопмент
   GoFuture от его имени) подаёт заявку: имя тенанта, целевой регион
   (`sgp`/`jkt`/`sao`/`core`, [Task3/01-region-selection.md](../Task3/01-region-selection.md)),
   ожидаемый масштаб, требуемый уровень изоляции (заполняется по
   критериям [01-tenancy-model.md](01-tenancy-model.md), при
   необходимости — согласуется с архитектурным комитетом для
   пограничных случаев), нужные локальные интеграции (платёжный/
   картографический провайдер), метаданные корпоративного IdP (если
   планируется SSO, [02-iam.md](02-iam.md)). Onboarding Service создаёт
   объект `Tenant` (CRD) со статусом `pending`.
   **Автоматизация**: API Onboarding Service + создание CRD.

2. **Создание realm в Keycloak.** Terraform (Keycloak provider) создаёт
   realm тенанта, дефолтные роли ([02-iam.md](02-iam.md)), клиентские
   приложения (мобильные приложения пассажира/водителя, сервисный
   аккаунт), и — если указано в заявке — конфигурацию федерации с
   корпоративным IdP партнёра (OIDC/SAML, [02-iam.md](02-iam.md)).
   **Автоматизация**: Terraform, вызывается Onboarding Service.

3. **Создание схемы БД / RLS-политик.** Для pool-тенанта: регистрация
   `tenant_id` в справочнике тенантов и проверка (автоматическим тестом,
   не вручную), что RLS-политики уже покрывают все таблицы, содержащие
   тенант-специфичные данные ([01-tenancy-model.md](01-tenancy-model.md)).
   Для silo-тенанта: Terraform создаёт выделенную схему/БД на каждый
   сервис и прогоняет стандартные миграции сервиса на новую
   схему/БД. **Автоматизация**: Terraform (провижининг) + существующие
   инструменты миграции схем сервисов.

4. **Создание топиков Kafka.** Для pool-тенанта: резервирование
   подмножества партиций существующих региональных топиков за
   `tenant_id` ([01-tenancy-model.md](01-tenancy-model.md)). Для
   silo-тенанта: Terraform (Kafka provider) создаёт выделенные топики
   `{region}.{tenant}.{domain}.{event}`. **Автоматизация**: Terraform.

5. **Настройка квот и rate limiting на API Gateway.** Onboarding Service
   применяет (через Terraform или напрямую через API/CRD Gateway)
   политику квот, соответствующую уровню изоляции и заявленному масштабу
   тенанта — ограничивает воздействие тенанта на общую ёмкость региона
   (особенно важно для pool). **Автоматизация**: Terraform/Kubernetes
   operator (объект конфигурации Gateway как CRD).

6. **Дашборды Grafana.** Provisioning параметризованных шаблонов
   дашбордов (переменная/метка `tenant_id`, дополняющая существующий
   мониторинг, [Task2/06-monitoring.md](../Task2/06-monitoring.md)) через
   Terraform (Grafana provider) — переиспользование готовых шаблонов, а не
   ручное создание дашборда с нуля на каждого тенанта. **Автоматизация**:
   Terraform.

7. **Конфигурация локальных платёжных и картографических провайдеров.**
   Onboarding Service настраивает Payments Service и Geography Service
   тенанта учётными данными нужного провайдера (получены из Secrets
   Manager, [Task3/06-security-rationale.md](../Task3/06-security-rationale.md)).
   Если регион и провайдер уже поддерживаются GoFuture — переиспользуется
   существующая интеграция; если нужен принципиально новый провайдер/
   регион — этот шаг зависит от отдельного, более длительного процесса
   ([Task3/01-region-selection.md](../Task3/01-region-selection.md),
   [Task3/05-compliance.md](../Task3/05-compliance.md)) и не укладывается
   в целевые 2–4 недели (см. риски). **Автоматизация**: Onboarding
   Service (вызовы API провайдеров) + Secrets Manager.

8. **Smoke-тесты.** Автоматический сквозной прогон: тестовое бронирование
   через полную сагу ([Task2/04-saga.md](../Task2/04-saga.md)) в
   изолированном тестовом контексте тенанта; попытка кросс-тенантного
   чтения данных, которая должна завершиться отказом (проверка RLS,
   [01-tenancy-model.md](01-tenancy-model.md)); проверка, что события
   несут верный `tenant_id` и попадают в ожидаемые партиции/топики;
   проверка входа через Keycloak (в т. ч. SSO, если настроен); проверка,
   что дашборд Grafana тенанта отображает данные; проверка срабатывания
   квот/rate limiting. Отказ любой проверки останавливает переход к
   следующему шагу и возвращает статус `Tenant` в `failed` с указанием
   причины. **Автоматизация**: пайплайн smoke-тестов, запускаемый
   Onboarding Service (тот же принцип, что и обязательные учения отката в
   [Task1/04-backward-compatibility.md](../Task1/04-backward-compatibility.md) —
   не считать этап завершённым без прохождения проверки).

9. **Активация.** Onboarding Service переводит статус `Tenant` в `active`;
   API Gateway начинает принимать боевой трафик realm/тенанта; партнёр
   уведомляется. **Автоматизация**: Kubernetes operator (финальный переход
   состояния CRD) + уведомление через Onboarding Service.

Диаграммы: [c2-multitenancy.puml](c2-multitenancy.puml) (целевая
архитектура IAM/мониторинга/квот), [c3-onboarding.puml](c3-onboarding.puml)
(поток данных самого процесса онбординга).

### Целевое время

- **Pool** — ближе к нижней границе 2–4 недель: почти всё
  переиспользуется (общая инфраструктура региона), основное время уходит
  на согласование заявки, интеграцию с корпоративным IdP партнёра (если
  есть) и локальные платёжные/картографические интеграции, если они для
  GoFuture не новые.
  **Silo (схема/БД)** — ближе к верхней границе 2–4 недель: дополнительное
  время на провижининг и миграцию выделенной схемы/БД, более полный набор
  smoke-тестов.
- **Silo (выделенный региональный стек)** — вне диапазона 2–4 недели;
  сопоставимо со сроком добавления нового региона GoFuture
  ([Task3/01-region-selection.md](../Task3/01-region-selection.md)) —
  недели-месяцы, включая выбор облачного провайдера, подтверждение 3+ зон
  доступности и, при необходимости, отдельный комплаенс-анализ
  ([Task3/05-compliance.md](../Task3/05-compliance.md)). Это отдельная
  категория проекта, а не расширенный онбординг.

## Альтернативы

- **Полностью ручной онбординг силами инженеров платформенной команды.**
  Отклонено: не масштабируется на цель "быстрый запуск партнёров в новых
  регионах" — линейно растущая нагрузка на платформенную команду с каждым
  новым партнёром противоречит самой бизнес-цели самообслуживания.
- **Только Terraform, без Kubernetes operator.** Отклонено: Terraform
  хорошо подходит для одноразового провижининга, но не для непрерывного
  согласования состояния (например, автоматической реакции на изменение
  уровня изоляции тенанта после его роста, [01-tenancy-model.md](01-tenancy-model.md))
  — без оператора эти сценарии потребовали бы повторного ручного запуска
  Terraform по инциденту/запросу, а не автоматического reconciliation.
- **Активация до прохождения smoke-тестов, с проверкой постфактум.**
  Отклонено: риск боевой утечки данных между тенантами
  (RLS-misconfiguration, [01-tenancy-model.md](01-tenancy-model.md)) при
  обнаружении постфактум значительно дороже, чем задержка активации на
  время прогона тестов.
- **Единый целевой срок 2–4 недели для всех уровней изоляции, включая
  выделенный региональный стек.** Отклонено: заведомо невыполнимое
  обещание — время добавления нового региона
  ([Task3/01-region-selection.md](../Task3/01-region-selection.md)) на
  порядок больше типового онбординга; лучше явно развести ожидания
  по уровням, чем дать единую цифру, которую платформа не сможет
  выполнить для части партнёров.

## Компромиссы и риски

- Автоматизация всех девяти шагов — существенная инвестиция в
  инструментарий (Terraform-модули, кастомный Kubernetes operator,
  пайплайн smoke-тестов) до того, как она окупится на первых партнёрах —
  для очень малого числа партнёров ручной процесс может первое время
  быть дешевле, но не соответствует заявленной цели масштабируемого
  самообслуживания.
- Kubernetes operator, управляющий реальными ресурсами (схемы БД,
  Kafka-топики, realm), — критичный компонент платформы: ошибка в логике
  reconciliation потенциально способна одновременно затронуть многих
  тенантов (например, некорректно применённое изменение квоты для всех
  pool-тенантов сразу) — требует собственного тщательного тестирования и
  постепенного раскатывания изменений самого оператора, а не только
  тенантов, которыми он управляет.
- Smoke-тесты проверяют состояние на момент онбординга, но не защищают от
  последующей регрессии (например, будущее изменение кода сервиса,
  забывшее установить `app.tenant_id`) — это отдельная задача постоянного
  мониторинга/тестирования, не решаемая одним прогоном при онбординге.
- Явное разведение сроков по уровням изоляции (см. "Целевое время") может
  создавать коммерческое давление на архитектуру — продажи могут
  обещать партнёру срок, не соответствующий фактически выбранному уровню
  изоляции; критерии выбора уровня ([01-tenancy-model.md](01-tenancy-model.md))
  должны применяться до коммерческого обещания срока, а не подгоняться под
  него.

## Статус

Предложено.
