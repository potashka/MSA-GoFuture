# ADR-T5-01: Модель изоляции данных мультитенантной платформы

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда

## Контекст

GoFuture переходит от единственного оператора платформы к модели, в
которой локальные партнёры (франчайзи/операторы такси под собственным
брендом) запускаются на общей инфраструктуре GoFuture в новых регионах —
"тенанты" поверх уже существующей архитектуры Database-per-Service
([Task1/02-service-map.md](../Task1/02-service-map.md)), событийной
платформы Kafka ([Task2/01-domain-events.md](../Task2/01-domain-events.md),
[Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)) и региональной
модели ([Task3/01-region-selection.md](../Task3/01-region-selection.md)).
Нужна модель изоляции данных между тенантами внутри одного региона,
покрывающая как небольших партнёров, для которых важна скорость и низкая
стоимость запуска, так и крупных партнёров с жёсткими собственными
регуляторными требованиями.

## Требования

- Полная изоляция данных между тенантами — тенант не должен иметь
  технической возможности прочитать данные другого тенанта ни при каком
  штатном сценарии использования платформы.
- Быстрый запуск нового стандартного партнёра — согласуется с целевым
  временем онбординга 2–4 недели ([03-onboarding.md](03-onboarding.md)).
- Для партнёров с собственными жёсткими регуляторными требованиями (в
  дополнение к региональной residency/cross-border policy из
  [Task3/05-compliance.md](../Task3/05-compliance.md)) — уровень изоляции,
  верифицируемый физически/на уровне схемы, а не только политикой доступа.
- Стоимость инфраструктуры на тенанта должна соответствовать масштабу и
  требованиям конкретного партнёра — не каждому партнёру нужна
  максимальная (и самая дорогая) изоляция.
- Каждое доменное событие ([Task2/01-domain-events.md](../Task2/01-domain-events.md))
  и каждая запись в БД должны быть однозначно привязаны к тенанту.

## Решение

**Гибридная схема с тремя уровнями изоляции** — pool, dedicated tier и
strict silo, выбираемыми на партнёра, а не единая модель для всех.

### Pool — для стандартных партнёров

- **Данные**: партнёры стандартного уровня делят общие таблицы тех же
  сервисных БД, что уже развёрнуты в регионе (Booking DB, Driver DB,
  Payments DB и т. д., [Task1/02-service-map.md](../Task1/02-service-map.md)).
  Каждая строка несёт обязательную колонку `tenant_id`.
- **Изоляция на уровне БД**: PostgreSQL **Row-Level Security fail-closed**.
  Каждая tenant-specific таблица включает `ENABLE ROW LEVEL SECURITY` и
  `FORCE ROW LEVEL SECURITY`, а политика содержит и `USING`, и `WITH
  CHECK`. Приложение устанавливает `SET LOCAL app.tenant_id` только внутри
  транзакции из проверенного claim токена (см. [02-iam.md](02-iam.md)).
  Если tenant context отсутствует, `current_setting('app.tenant_id',
  true)` возвращает `NULL`, сравнение с `tenant_id` не проходит, и доступ
  запрещается. Это даёt защиту на уровне СУБД, а не только на уровне
  корректности application-кода.
- **Изоляция в Kafka для pool**: стандартные tenants используют shared
  regional topics (`{region}.{domain}.{event}`,
  [Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)). Каждое событие
  обязательно несёт `tenant_id` в envelope, а Kafka record key строится как
  `tenant_id:business_key`. Для Booking это `tenant_id:booking_id`; для
  `DriverLocationUpdated` — `tenant_id:region_id:driver_id` либо
  `tenant_id:driver_id` внутри отдельного регионального топика, сохраняя
  модель Task2, где порядок и compaction идут по водителю. Producer
  обязан проверять tenant context до публикации, consumer — сверять
  `tenant_id` envelope с разрешённым tenant context/consumer group перед
  обработкой. Kafka ACL применяются на topic/consumer group/client level;
  ACL на отдельную partition не является механизмом изоляции.
- **Noisy neighbor controls для pool Kafka**: изоляция производительности
  обеспечивается producer/consumer quotas, rate limiting на Gateway,
  отдельными consumer groups для tenant-aware consumers, лимитами
  concurrency/backpressure в consumers и алертами по tenant tier. Метрики
  не используют сырой `tenant_id` как безграничную label-кардинальность:
  основная агрегация идёт по `tenant_tier`, `region_id`, service и topic,
  а drill-down по конкретному tenant включается в ограниченных dashboards
  или на время incident investigation.
- **Стоимость**: минимальные предельные затраты на тенанта — общая
  инфраструктура амортизируется между всеми pool-тенантами региона.
  Самое быстрое время онбординга ([03-onboarding.md](03-onboarding.md)).

### PostgreSQL RLS fail-closed

RLS применяется ко всем таблицам, где есть tenant-specific rows. Пример
для Booking DB:

```sql
ALTER TABLE bookings ENABLE ROW LEVEL SECURITY;
ALTER TABLE bookings FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON bookings
USING (
  tenant_id = current_setting('app.tenant_id', true)::uuid
)
WITH CHECK (
  tenant_id = current_setting('app.tenant_id', true)::uuid
);
```

`current_setting('app.tenant_id', true)` при отсутствии tenant context
возвращает `NULL`; выражение `tenant_id = NULL::uuid` не истинно, поэтому
строки не читаются и новые строки не проходят `WITH CHECK`. Это и есть
fail-closed поведение. Сервис устанавливает tenant context только внутри
явной транзакции:

```sql
BEGIN;
SET LOCAL app.tenant_id = '00000000-0000-0000-0000-000000000001';
-- application queries
COMMIT;
```

Эксплуатационные ограничения:

- application role не является `superuser`, не имеет `BYPASSRLS` и не
  является owner таблиц; владельцем таблиц является отдельная migration
  role, недоступная runtime-сервису;
- все запросы к tenant tables выполняются внутри transaction boundary с
  `SET LOCAL`, а не через session-level `SET`;
- connection pool сбрасывает session state при возврате соединения
  (`DISCARD ALL`/pool reset hook или эквивалент), а сервис запрещает
  повторное использование tenant context между запросами;
- попытка выполнить запрос без tenant context, с tenant mismatch или из
  platform support mode логируется как security/audit event;
- миграции и новые таблицы проходят automated checks: RLS enabled,
  `FORCE ROW LEVEL SECURITY`, есть `USING` и `WITH CHECK`, runtime role не
  owner.

Negative tests обязательны для каждого сервиса с tenant data:

| Тест | Ожидаемый результат |
|---|---|
| Tenant A читает строки Tenant A | Разрешено |
| Tenant A читает строки Tenant B | Deny / 0 rows |
| Tenant A пишет строку с `tenant_id` Tenant B | Deny через `WITH CHECK` |
| Запрос без `SET LOCAL app.tenant_id` | Deny / 0 rows; audit event |
| Platform break-glass читает tenant data | Только через time-bound elevation, MFA, ticket/reason; доступ логируется и ограничен scope |

### Dedicated и strict silo — для крупных партнёров

- **Dedicated tier для крупных tenants**: отдельная схема PostgreSQL или
  отдельная БД на tenant в рамках регионального кластера на каждый сервис
  вместо общих таблиц + RLS. Kafka — тот же региональный кластер, но
  dedicated topics (`{region}.{tenant}.{domain}.{event}`), отдельные
  quotas, отдельные service accounts/ACL и отдельные encryption keys/KMS
  key aliases для данных tenant. Это снижает noisy neighbor risk и даёт
  лучшее операционное разделение без полного отдельного стека.
- **Уровень "выделенный региональный стек"** — для партнёров с наиболее
  жёсткой собственной регуляторикой: не просто отдельная схема/топики
  внутри существующего регионального стека, а фактически отдельное
  развёртывание всей архитектуры региона
  ([Task3/01-region-selection.md](../Task3/01-region-selection.md)) под
  этого тенанта — вплоть до отдельного облачного аккаунта/кластера,
  отдельной БД/схемы, а при необходимости отдельного Kafka cluster. Это
  количественно тот же процесс, что и добавление нового региона GoFuture
  (см. [Task3/01-region-selection.md](../Task3/01-region-selection.md)),
  только триггер — требование конкретного партнёра, а не собственное
  решение GoFuture о выходе на рынок. Соответственно, и стоимость, и время
  этого варианта сопоставимы с добавлением региона, а не с онбордингом
  партнёра (см. риски).
- **Стоимость**: заметно выше pool — отдельная схема/БД дешевле
  выделенного регионального стека, но оба варианта дороже pool за счёт
  отказа от амортизации инфраструктуры между тенантами.

### Критерии выбора уровня изоляции

| Критерий | Pool | Dedicated tier | Strict silo |
|---|---|---|---|
| Ожидаемый масштаб партнёра | Малый/средний | Средний/крупный | Крупнейшие партнёры |
| Собственная регуляторика партнёра сверх регионального законодательства | Отсутствует | Требует структурного, а не только политикой, разделения данных | Требует физически обособленной инфраструктуры (например, отдельный юридический периметр обработки) |
| Готовность платить за изоляцию | Низкая/стандартный тариф | Повышенный тариф | Индивидуальный контракт |
| Допустимость риска "шумного соседа" | Приемлема при quotas/rate limits/backpressure и мониторинге по tenant tier (см. [03-onboarding.md](03-onboarding.md)) | Низкая: dedicated topics/quotas/keys | Минимальная: отдельный стек/cluster |
| Целевое время запуска | 2–4 недели | Ближе к верхней границе 2–4 недель | Сопоставимо со сроком добавления региона ([Task3/01-region-selection.md](../Task3/01-region-selection.md)) — не 2–4 недели |

Решение об уровне для конкретного партнёра принимается на этапе заявки
([03-onboarding.md](03-onboarding.md)) по этим критериям, а не выбирается
партнёром произвольно — GoFuture сохраняет право поднять уровень
изоляции для партнёра, чей профиль риска/масштаб вырос после запуска.

## Альтернативы

- **Чистый pool для всех партнёров без исключений.** Отклонено:
  не покрывает партнёров с собственной жёсткой регуляторикой, для
  которых политика (RLS) — не структурное доказательство изоляции;
  крупный партнёр с таким требованием либо не смог бы быть принят на
  платформу, либо получил бы неадекватную своим рискам модель.
- **Чистый silo для всех партнёров без исключений.** Отклонено: для
  небольшого партнёра выделенная схема/БД или тем более отдельный
  региональный стек избыточны по стоимости и времени запуска —
  противоречит целевому времени онбординга 2–4 недели
  ([03-onboarding.md](03-onboarding.md)) для типового партнёра и
  сделало бы платформу невыгодной для малых партнёров, ради которых во
  многом и строится модель самообслуживания.
  Единый уровень изоляции для всех устраняет саму возможность
  предлагать партнёрам выбор, соразмерный их профилю риска и готовности
  платить.
- **Изоляция только на уровне Kafka (партиции/топики) без RLS в БД.**
  Отклонено: события — не единственный путь к данным; сервисные БД
  остаются точкой, где возможна утечка между тенантами без RLS, даже если
  событийный слой полностью изолирован.
- **Изоляция только на уровне БД (RLS) без обязательного `tenant_id` в
  событиях.** Отклонено: событие без `tenant_id` в конверте не может быть
  корректно маршрутизировано в карантин/аналитику/BI по тенанту
  ([Task4/01-data-pipeline.md](../Task4/01-data-pipeline.md)) и не
  позволяет проверить tenant context на producer/consumer boundary — оба
  механизма (RLS и `tenant_id` в событии) необходимы одновременно, а не
  взаимозаменяемы.
- **Фиксированные наборы Kafka partitions как основной способ изоляции
  pool-tenants.** Отклонено: стандартная Kafka-модель не даёт полноценный
  ACL на отдельную partition, а резервирование partition set плохо
  масштабируется при росте числа tenants и изменении нагрузки. Pool
  использует shared topics, ключ `tenant_id:business_key`, quotas,
  tenant-aware producer/consumer checks и отдельные consumer groups.

## Компромиссы и риски

- RLS корректна ровно настолько, насколько корректно каждое соединение
  устанавливает `app.tenant_id` — ошибка в этом месте кода сервиса
  (например, переиспользование соединения из пула без сброса контекста
  тенанта) — самый вероятный практический вектор утечки в pool-модели;
  требует обязательного автоматизированного теста именно этого сценария
  на этапе онбординга (см. smoke-тесты, [03-onboarding.md](03-onboarding.md))
  и не должно полагаться только на код-ревью.
- Shared Kafka topics для pool-tenants не дают физической изоляции
  throughput между tenants. Noisy neighbor risk смягчается quotas,
  Gateway rate limits, consumer backpressure, tenant-tier alerting и
  возможностью перевести крупного tenant на dedicated topics/quotas/keys.
- Silo на уровне "выделенный региональный стек" — по сути открытие нового
  региона под одного партнёра; ошибочно обещать этот уровень в рамках
  типового цикла онбординга — должен явно продаваться/планироваться как
  отдельный проект с собственным сроком, а не как "тариф" в том же ряду,
  что pool и silo-схема.
- Рост числа тенантов увеличивает кардинальность меток `tenant_id` в
  метриках/логах ([Task2/06-monitoring.md](../Task2/06-monitoring.md)) —
  поэтому базовые метрики агрегируются по `tenant_tier`/region/service, а
  drill-down по конкретному tenant включается ограниченно. Иначе стоимость
  Prometheus/Loki и стабильность observability деградируют быстрее, чем
  сама tenant isolation.

## Статус

Предложено.
