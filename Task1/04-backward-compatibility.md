# ADR-T1-04: Механизмы обратной совместимости на время миграции

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда

## Контекст

Декомпозиция монолита GoFuture идёт по стратегии Strangler Fig поэтапно (см.
[03-decomposition-order.md](03-decomposition-order.md)): на каждом этапе часть
трафика уже обслуживается новым доменным сервисом, а часть — всё ещё
монолитом (см. диаграмму [c2-to-be.puml](c2-to-be.puml), где монолит показан
как "усыхающий" контейнер за тем же API Gateway). В переходный период клиенты
(мобильные приложения, веб-портал, админ-панель), сам монолит и уже вынесенные
сервисы должны продолжать взаимодействовать корректно, без синхронизированных
релизов "всё сразу" и без простоя (требование Д1, [01-nfr.md](01-nfr.md)).

Нужно зафиксировать набор механизмов, которые позволяют:
- постепенно переключать трафик с монолита на сервис и обратно;
- откатываться на монолитный путь мгновенно при инциденте;
- не ломать контракт для клиентов, пока часть функциональности мигрирует;
- обнаруживать расхождение контрактов до того, как оно попадёт в прод.

## Требования

- Откат на монолитный путь должен быть мгновенным и не требовать
  redeploy — то есть управляться конфигурацией/флагом, а не релизом кода
  (согласуется с требованием Э4, [01-nfr.md](01-nfr.md), о независимом
  деплое, и с целевым MTTR < 1 часа, требование Э1).
- Клиентские приложения (мобильные, веб-портал) не должны знать, какой
  бэкенд (монолит или сервис) обслуживает конкретный запрос.
- Версии публичных API, на которые уже интегрированы клиенты, не должны
  ломаться при выносе сервиса из монолита.
- Расхождения в контрактах между потребителями и вновь выделенными
  сервисами должны обнаруживаться в CI, а не в проде (согласуется с
  требованием Э2 — сборка < 15 минут — как бюджет времени на прогон
  contract-тестов).

## Решение

### 1. API Gateway с постепенным переключением маршрутов

API Gateway (см. [02-service-map.md](02-service-map.md),
[c2-to-be.puml](c2-to-be.puml)) — единая точка входа для всех клиентов.
Переключение конкретного маршрута (например, `POST /v1/bookings`) с монолита
на новый сервис выполняется на уровне маршрутизации Gateway, а не на уровне
клиента:

- Маршрутизация по процентной доле трафика (canary): часть запросов
  направляется в новый сервис (через Anti-Corruption Layer), остальное — в
  монолит, с постепенным увеличением доли сервиса до 100%.
- Возможность мгновенно вернуть маршрут целиком на монолит без релиза
  клиентских приложений.
- Маршрутизация видна и управляется одинаково для всех типов клиентов
  (мобильные приложения, веб-портал, админ-панель), которые обращаются
  только к Gateway и не знают о фактическом бэкенде.

### 2. Версионирование API (заморозка v1)

- Публичный контракт API Gateway версионируется (`v1`, `v2`, ...).
  Контракт `v1`, на который уже интегрированы клиентские приложения,
  замораживается на время миграции конкретного домена: поведение и формат
  ответа не меняются независимо от того, кто фактически обрабатывает
  запрос — монолит или новый сервис.
- Новая функциональность, требующая изменения контракта, выпускается под
  `v2` (или соответствующей минорной версией), не затрагивая `v1`.
- ACL (Anti-Corruption Layer) отвечает за трансляцию `v1`-контракта
  монолита в контракт нового доменного сервиса и обратно, пока `v1` не
  будет выведен из эксплуатации по согласованному графику после того, как
  все клиенты перейдут на актуальную версию.

### 3. Feature flags с мгновенным откатом на монолитный путь

- Каждый вынесенный доменный маршрут закрывается feature-флагом
  уровня Gateway/ACL: `use_<domain>_service = true|false`.
- При включённом флаге трафик идёт в новый сервис; при выключенном —
  маршрутизация мгновенно возвращается в монолит без redeploy, по
  изменению конфигурации.
- Флаг обязателен для каждого этапа декомпозиции (см.
  [03-decomposition-order.md](03-decomposition-order.md)) и остаётся
  включённым в сторону мгновенного отката до тех пор, пока этап не признан
  завершённым по критериям готовности соответствующего этапа.
- Откат по флагу — часть обязательных учений (game day) перед объявлением
  этапа завершённым.

### 4. Anti-Corruption Layer (ACL)

- Отдельный компонент (см. [c2-to-be.puml](c2-to-be.puml)), стоящий между
  API Gateway и доменными сервисами/монолитом.
- Транслирует модели и контракты монолита (устаревшие форматы, доменные
  понятия AS-IS) в модели новых сервисов и обратно, не давая устаревшим
  представлениям "протечь" в новые bounded context (см.
  [02-service-map.md](02-service-map.md)).
- Позволяет каждому новому сервису проектировать свою модель данных и API
  исходя из целевого домена, а не из ограничений схемы монолита.
- ACL — временный компонент программы миграции: по мере того как всё
  больше клиентов работает напрямую по актуальному контракту сервиса, а
  `v1` выводится из эксплуатации, зависимость от ACL для конкретного домена
  снижается вплоть до вывода из эксплуатации после завершения этапа.

### 5. Contract-тесты

- Между потребителями событий/API (Booking, Notification, Fraud,
  Analytics и др., см. [02-service-map.md](02-service-map.md)) и
  издателями заключаются потребительские contract-тесты (consumer-driven
  contracts): каждый потребитель фиксирует ожидаемую форму
  события/ответа API.
- Contract-тесты выполняются в CI при каждом изменении издателя
  (входит в бюджет сборки < 15 минут, требование Э2) и блокируют релиз при
  расхождении с зафиксированным контрактом.
- Особое внимание — событиям, потребляемым многими доменами
  одновременно (например, `TripCompleted`, потребляемый Payments,
  Payouts, Notification, Fraud, Analytics): изменение схемы такого события
  проверяется против контрактов всех известных потребителей.
- Contract-тесты обязательны и для CDC-потока из монолита (см.
  [05-data-migration-plan.md](05-data-migration-plan.md)) — потребители
  CDC-событий фиксируют ожидаемую форму данных, изменившихся в монолитной
  БД.

## Альтернативы

- **Синхронизированные релизы клиента и бэкенда на каждом этапе выноса
  сервиса.** Отклонено: требует координации релизов мобильных приложений
  (проходящих модерацию сторов) с бэкендом, что противоречит требованию
  time-to-market ≤ 2 недели (Э3) и делает откат медленным и рискованным.
- **Прямой вызов клиентами вынесенных сервисов, минуя Gateway.**
  Отклонено: ломает единую точку контроля переключения трафика и
  версионирования, каждый клиент должен был бы знать топологию бэкенда —
  противоречит принципу единой точки входа.
- **Отказ от ACL, прямая интеграция сервисов с моделью данных монолита.**
  Отклонено: закрепляет протечку модели монолита в новые bounded context,
  что подрывает саму цель декомпозиции (см.
  [02-service-map.md](02-service-map.md)) и усложняет последующий вывод
  монолита из эксплуатации.
- **Полагаться только на мониторинг постфактум вместо contract-тестов.**
  Отклонено: обнаружение расхождения контракта в проде вместо CI
  напрямую конфликтует с целевым MTTR < 1 часа (Э1) и с требованием
  доступности критических сервисов (Д1).

## Компромиссы и риски

- ACL и feature-флаги — временная, но реальная эксплуатационная нагрузка:
  дополнительный компонент в пути запроса (латентность, точка отказа),
  который необходимо мониторить и выводить из эксплуатации по мере
  завершения этапов, иначе он рискует стать постоянной частью архитектуры.
- Заморозка `v1` ограничивает эволюцию контракта в течение всего периода
  миграции конкретного домена — команда не может свободно менять форму
  ответа, пока не выведены старые клиенты; это сдерживающий фактор для
  time-to-market именно на замороженных путях.
- Consumer-driven contract-тесты требуют дисциплины поддержания в
  актуальном состоянии со стороны каждой потребляющей команды (особенно
  "широких" потребителей — Notification, Fraud, Analytics, см.
  [02-service-map.md](02-service-map.md)); риск "протухания" тестов при
  недостаточной вовлечённости команд.
- Feature-флаги увеличивают комбинаторную сложность тестирования (сервис
  включён/выключен × разные домены на разных этапах) — требуется явная
  матрица тестовых сценариев для переходного периода, а не просто тесты
  "как в проде сейчас".
