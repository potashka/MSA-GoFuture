# ADR-T1-01: Нефункциональные требования к целевой архитектуре GoFuture

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture

## Контекст

Компания GoFuture переходит от монолита (Django + Celery + RabbitMQ, единая
PostgreSQL) к микросервисной архитектуре по стратегии Strangler Fig с
Database-per-Service (см. [docs/context.md](../docs/context.md)). Текущая
архитектура не удовлетворяет целевым бизнес-требованиям: MTTR превышает 4 часа,
сборка занимает более 30 минут, масштабирование только вертикальное и ручное, а
9 доменных модулей (Booking, Driver, Pricing, Payments, Payouts, Notification,
Geography, Analytics, Fraud) обращаются к общей базе напрямую через границы
доменов.

Прежде чем приступать к декомпозиции, необходимо зафиксировать измеримые
нефункциональные требования (НФТ), которые станут контрактом между доменными
командами, платформенной командой, SRE и архитектурным комитетом на всё время
миграции. Без этого базового набора целевых показателей невозможно ни
проектировать сервисы, ни оценивать готовность каждого этапа декомпозиции (см.
[03-decomposition-order.md](03-decomposition-order.md)).

## Требования

Источники требований — бизнес-цели, зафиксированные в
[docs/context.md](../docs/context.md):

- 500 тыс. конкурентных поездок.
- Горизонтальное масштабирование в 3+ географических регионах (Юго-Восточная
  Азия, Южная Америка и далее).
- Доступность 99,95% критических сервисов.
- Time-to-market новых функций — 2 недели.
- Соответствие локальным регуляторным требованиям (data residency).
- Динамическое ценообразование и «умное» перераспределение водителей в
  реальном времени.

## Решение

Зафиксировать следующий набор измеримых НФТ по категориям. Целевые значения —
предложение архитектурного комитета для дальнейшего согласования с
продуктовыми командами и SRE.

### 1. Производительность

| # | Требование | Целевое значение |
|---|---|---|
| П1 | Общая пропускная способность платформы | 500 000 одновременных активных поездок в состоянии "в процессе" (booking-to-completion) распределённо по всем регионам |
| П2 | Latency создания заказа (Booking: приём заявки до подтверждения бронирования, включая синхронный запрос котировки и матчинга) | p95 ≤ 300 мс, p99 ≤ 800 мс, измеряется на границе API Gateway |
| П3 | Latency обновления локации водителя (приём геопозиции сервисом Driver) | p95 ≤ 150 мс на приём одного события; частота приёма — не реже 1 обновления на водителя каждые 3–5 сек в активном статусе |
| П4 | Latency расчёта цены (Pricing: синхронный вызов из Booking) | p95 ≤ 200 мс, p99 ≤ 500 мс |
| П5 | Пропускная способность события локации водителя (агрегированно по платформе) | автоскейлинг должен покрывать пиковую нагрузку часа пик в самом крупном регионе без деградации П3 |

### 2. Доступность

| # | Требование | Целевое значение |
|---|---|---|
| Д1 | Доступность критических сервисов (Booking, Driver, Pricing, Payments, API Gateway, Identity) | 99,95% (допустимый простой ≈ 21,9 мин/месяц на сервис) |
| Д2 | Доступность некритических сервисов (Analytics, Notification, Fraud — асинхронный контур) | 99,9% |
| Д3 | RTO/RPO — Tier 1: Booking, Driver, Pricing, Payments (денежные и операционные потоки в реальном времени) | RTO ≤ 5 мин, RPO ≤ 1 мин (либо near-zero для Payments за счёт идемпотентности и синхронной репликации транзакционного лога) |
| Д4 | RTO/RPO — Tier 2: Payouts, Notification, Geography (не блокируют текущую поездку синхронно) | RTO ≤ 15 мин, RPO ≤ 5 мин |
| Д5 | RTO/RPO — Tier 3: Fraud (асинхронный скоринг), Analytics | RTO ≤ 4 ч, RPO ≤ 1 ч |

### 3. Масштабируемость

| # | Требование | Целевое значение |
|---|---|---|
| М1 | Горизонтальное масштабирование | каждый доменный сервис — stateless (либо с внешним stateful-хранилищем) и масштабируется добавлением реплик без ручного вмешательства |
| М2 | Географическое распределение | развёртывание минимум в 3 регионах (в т.ч. Юго-Восточная Азия, Южная Америка) с возможностью независимого масштабирования каждого региона |
| М3 | Автоскейлинг | автоматическое горизонтальное масштабирование (Kubernetes HPA) по метрикам нагрузки (RPS, глубина очереди Kafka, насыщенность CPU/памяти) без ручных операций |
| М4 | Независимость масштабирования сервисов | пиковая нагрузка на Driver/Geography (высокочастотные обновления локации) не должна требовать масштабирования Payments/Payouts и наоборот |

### 4. Безопасность

| # | Требование | Целевое значение |
|---|---|---|
| Б1 | Межсервисное взаимодействие | обязательный mTLS между всеми доменными сервисами и платформенными компонентами (API Gateway, Identity Service) |
| Б2 | Аутентификация и авторизация | централизованный IAM через Identity Service; ни один сервис не хранит и не проверяет пароли самостоятельно |
| Б3 | Резидентность данных (data residency) | персональные и регуляторно значимые данные (профили, платежи, выплаты) не покидают регион, в котором они созданы, без явного регуляторного основания |
| Б4 | Изоляция данных по доменам | каждый сервис владеет собственной БД (Database-per-Service); прямой SQL-доступ к чужой БД запрещён на архитектурном уровне |

### 5. Эксплуатируемость

| # | Требование | Целевое значение |
|---|---|---|
| Э1 | MTTR | < 1 часа для критических сервисов (против текущих > 4 часов у монолита) |
| Э2 | Время сборки | < 15 минут на сервис (против текущих > 30 минут для монолита) |
| Э3 | Время вывода новой функциональности (time-to-market) | ≤ 2 недели от постановки задачи до продакшена для типовой доменной функции |
| Э4 | Независимость деплоя | каждый доменный сервис деплоится независимо от остальных и от монолита, без координационного окна простоя |

### 6. Согласованность данных

| # | Требование | Целевое значение |
|---|---|---|
| С1 | Модель согласованности по умолчанию | eventual consistency между доменами через события (Kafka); синхронные вызовы — только там, где немедленный ответ обязателен (например, котировка цены при создании заказа) |
| С2 | Денежные потоки (Booking → Payments → Payouts) | согласованность обеспечивается паттерном Saga (хореография или оркестрация) с компенсирующими транзакциями; недопустимы неявные распределённые транзакции (2PC) |
| С3 | Идемпотентность | все операции, инициируемые событиями или ретраями (особенно в Payments/Payouts), должны быть идемпотентны по бизнес-ключу операции |
| С4 | Обнаружение расхождений при миграции данных | автоматическая сверка (reconciliation) между старой и новой моделью данных на переходный период shadow/canary с одним authoritative writer для каждой бизнес-сущности, см. [05-data-migration-plan.md](05-data-migration-plan.md) |

## Альтернативы

- **Единая доступность 99,99% для всех сервисов.** Отклонено: избыточно
  дорого для некритических асинхронных доменов (Analytics, Notification,
  Fraud) и не соответствует их бизнес-роли; вместо этого введена
  дифференциация по классам (Tier 1/2/3).
- **Строгая (сильная) согласованность через распределённые транзакции
  между доменами.** Отклонено: 2PC/XA плохо масштабируется горизонтально и
  противоречит требованию независимого масштабирования и деплоя сервисов;
  выбран Saga + eventual consistency.
- **Единый глобальный latency-бюджет без разбивки по операциям.** Отклонено:
  операции разной природы (создание заказа, поток геолокации, расчёт цены)
  имеют разные профили нагрузки и критичности, единый бюджет либо избыточно
  жёсткий, либо маскирует деградацию отдельных операций.
- **RTO/RPO, единые для всех сервисов.** Отклонено: денежные и
  операционные сервисы реального времени требуют существенно более жёстких
  показателей, чем аналитический контур; единые показатели либо завышают
  стоимость Tier 3, либо занижают надёжность Tier 1.

## Компромиссы и риски

- Eventual consistency между доменами усложняет отладку и требует
  дисциплины в проектировании событий (идемпотентность, версионирование схем,
  отслеживание причинности) — риск временных несогласованностей, видимых
  пользователю (например, задержка отображения статуса поездки).
- Saga для денежных потоков требует реализации компенсирующих транзакций в
  Payments и Payouts до их выделения из монолита — дополнительная сложность,
  которую нельзя отложить (см. очерёдность в
  [03-decomposition-order.md](03-decomposition-order.md), пункт 5).
- Жёсткие latency-бюджеты (П2–П4) при синхронном взаимодействии Booking с
  Pricing и Driver создают риск каскадных таймаутов при деградации
  зависимого сервиса — требуются circuit breaker и таймауты с деградацией
  (fallback на последнюю известную котировку/эвристику матчинга).
- Data residency (Б3) может потребовать регионально изолированных
  инстансов сервисов и данных, что усложняет глобальную аналитику
  (Analytics) — потребуется отдельная стратегия агрегации обезличенных
  данных между регионами.
- Целевые значения в этом документе — отправная точка; они должны быть
  провалидированы нагрузочным тестированием на этапе пилота (см. Notification
  и Geography в [03-decomposition-order.md](03-decomposition-order.md)) и
  скорректированы при необходимости.

## Статус

Предложено.
