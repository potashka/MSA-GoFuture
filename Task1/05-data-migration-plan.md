# ADR-T1-05: План миграции данных из монолита в доменные сервисы

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда, data-инженеры

## Контекст

В AS-IS все 9 доменных модулей (Booking, Driver, Pricing, Payments, Payouts,
Notification, Geography, Fraud, Analytics) хранят данные в единой PostgreSQL и
обращаются к ним напрямую через SQL, пересекая границы доменов (см.
[docs/context.md](../docs/context.md)). Целевая архитектура —
Database-per-Service (требование Б4, [01-nfr.md](01-nfr.md)): у каждого
сервиса своя база (см. карту сервисов в
[02-service-map.md](02-service-map.md) и диаграмму
[c2-to-be.puml](c2-to-be.puml)).

Перенос данных должен происходить без остановки платформы и без потери
данных, при большом объёме операций (500 тыс. конкурентных поездок,
требование П1, [01-nfr.md](01-nfr.md)). Для этого используется единый
пошаговый пайплайн миграции данных, применяемый на каждом этапе декомпозиции
(см. очерёдность в [03-decomposition-order.md](03-decomposition-order.md)).

## Требования

- Нулевая потеря данных при переносе; возможность отката на любом шаге до
  момента вывода старых таблиц из эксплуатации.
- Расхождения между старой и новой моделью данных обнаруживаются
  автоматической сверкой (reconciliation) до переключения записи
  (требование С4, [01-nfr.md](01-nfr.md)).
- Для денежных потоков (Payments, Payouts) — расхождение при сверке перед
  переключением записи недопустимо (требование С2, С4,
  [01-nfr.md](01-nfr.md)): 100% совпадение обязательно.
- Миграция не должна требовать остановки записи дольше, чем допускает
  доступность соответствующего класса сервиса (Д1–Д5, [01-nfr.md](01-nfr.md)).

## Решение

Основной принцип миграции: **в каждый момент времени для конкретной
бизнес-сущности существует один authoritative writer**. До cutover им обычно
остаётся монолит, после cutover — новый доменный сервис. CDC используется
только как однонаправленный поток изменений от текущего владельца записи к
целевому хранилищу на этапе подготовки, а не как способ поддерживать две
равноправные системы записи.

Граница Database-per-Service сохраняется и во время миграции: новый сервис не
читает и не изменяет таблицы другого сервиса напрямую. Доступ к чужим данным
идёт через API, доменные события или временный CDC-поток из монолитной БД,
пока монолит ещё является владельцем записи для соответствующей сущности.

### Общий пайплайн миграции (применяется к каждому сервису)

1. **Определить владельца данных.** Для каждой бизнес-сущности фиксируется
   текущий authoritative source и будущий владелец записи. До cutover команды
   записи идут только в монолит; новый сервис не пишет назад в монолитные
   таблицы и не становится вторым равноправным writer.
2. **Создать Service DB.** Новый сервис получает собственную БД и схему,
   соответствующую его bounded context (см.
   [02-service-map.md](02-service-map.md)). Схема не должна требовать прямого
   SQL-доступа к таблицам других сервисов.
3. **Snapshot/backfill.** Исторические данные переносятся из монолитной БД в
   Service DB через snapshot, bulk export/import или доменно-специфичный
   backfill. Для Geography допускается технологический reindex в
   Elasticsearch; для Analytics — построение витрин из исторического CDC.
4. **Односторонний CDC `Monolith DB → Service DB`.** После snapshot
   включается Debezium/Kafka-поток из WAL монолитной PostgreSQL в сторону
   Service DB, чтобы догонять изменения, пока монолит остаётся единственным
   writer (см. [c2-to-be.puml](c2-to-be.puml): `monolithDb → cdc → kafka`).
   Двусторонний CDC не используется как основной механизм.
5. **Shadow reads.** Новый сервис обслуживает теневой поток чтений и/или
   расчётов без влияния на пользовательский результат. Production-команды
   записи всё ещё принимает authoritative writer текущего этапа.
6. **Reconciliation (сверка).** Автоматическое сравнение состояния данных
   монолита и нового сервиса (построчно, по контрольным суммам или по
   бизнес-агрегатам, в зависимости от домена) на протяжении контрольного
   периода. Критерий успеха сверки определяется индивидуально для каждого
   сервиса (см. таблицу ниже) в зависимости от цены ошибки в домене.
7. **Переключение чтения.** Читающие запросы (свои и через ACL) переводятся
   на новый сервис первыми — при обнаружении проблемы откат чтения на
   монолит не требует отмены уже принятых бизнес-решений.
8. **Canary команд записи.** Небольшой процент команд записи переводится на
   новый сервис через API Gateway/ACL. Для этих сущностей authoritative
   writer становится сервис; для остального трафика владельцем остаётся
   монолит. Разделение выполняется по стабильному ключу маршрутизации
   (регион, tenant, hash user/order id), чтобы одна и та же бизнес-сущность
   не принимала команды записи в двух местах.
9. **Service as sole writer.** После успешного canary весь поток команд
   записи для домена переводится на новый сервис, а монолит перестаёт
   изменять соответствующие таблицы. Если ещё не мигрировавшим частям
   монолита нужны уведомления о новых изменениях, сервис временно публикует
   compatibility events или read-model updates обратно в монолитный контур.
   Это не двусторонний CDC и не второй writer: источник истины остаётся в
   Service DB.
10. **Отключение CDC и старых таблиц.** После стабилизации, подтверждения
    отсутствия прямых читателей старых таблиц и выполнения retention/audit
    процедур CDC `Monolith DB → Service DB` отключается, старые таблицы
    архивируются и выводятся из эксплуатации.

Обычная запись из приложения сразу в две БД не используется как базовый
сценарий: при частичном успехе одна БД фиксирует изменение, а другая нет;
расхождения трудно обнаружить до бизнес-инцидента; двусторонние попытки
синхронизации создают риск циклической репликации; rollback становится
сложным, потому что нужно откатывать уже принятые решения в двух моделях; и
главное — теряется единый владелец записи. Кратковременный контролируемый
dual-write допустим только как исключение вокруг transactional outbox:
команда фиксируется одним authoritative writer, изменения публикуются через
outbox, операции идемпотентны, а reconciliation блокирует расширение трафика
при расхождениях.

### Rollback после переключения writer

После шага 8 или 9 откат не означает автоматическую запись в обе БД. Это
управляемая процедура:

1. Переключить feature flag/API routing на прежний маршрут для новых команд
   или остановить расширение canary.
2. Остановить новые команды записи на затронутом сегменте, если есть риск
   нарушения RPO/RTO соответствующего класса.
3. Дренировать очереди Kafka/outbox и убедиться, что нет незафиксированных
   команд или повторов.
4. Выполнить reconciliation между текущим authoritative source и целевой
   моделью.
5. Принять явное go/no-go решение об обратном переключении writer. При
   необходимости выполнить разовый обратный экспорт состояния, а не включать
   двусторонний CDC.

## Альтернативы

- **Полная одномоментная миграция данных ("big bang cutover") на каждом
  сервисе.** Отклонено: противоречит требованию минимизации простоя и
  общей стратегии Strangler Fig; не даёт времени на сверку и увеличивает
  риск необратимой потери/порчи данных при большом объёме (требование П1).
- **Snapshot без CDC (разовый перенос + периодические синхронизации).**
  Отклонено как стратегия по умолчанию: не обеспечивает актуальности
  данных при непрерывной записи в монолит в период миграции; используется
  точечно только там, где меняется сама технология хранения (Geography →
  Elasticsearch), в сочетании с последующим CDC, а не вместо него.
- **Обычный dual-write из приложения сразу в монолитную БД и Service DB.**
  Отклонено как базовая стратегия: частичный успех записи создаёт
  расхождение данных, попытки автоматической синхронизации ведут к
  циклической репликации, rollback требует ручного восстановления обеих
  моделей, а система теряет единого authoritative writer. Кратковременная
  контролируемая запись через transactional outbox допустима только как
  технический мост внутри одного cutover-окна, с идемпотентностью,
  reconciliation и явным владельцем записи.
- **Двусторонний CDC между монолитом и Service DB.** Отклонено как основной
  механизм: он маскирует границу владения данными, создаёт риск циклов и
  конфликтов записей и усложняет расследование инцидентов. После cutover
  сервис может временно публиковать compatibility events/read-model updates
  обратно в монолитный контур, но это не делает монолит writer.
- **Ручная сверка вместо автоматической.** Отклонено: не масштабируется
  на объём данных (500 тыс. конкурентных поездок) и не укладывается в
  целевые сроки перехода между этапами
  ([03-decomposition-order.md](03-decomposition-order.md)).

## Компромиссы и риски

- Snapshot/backfill, CDC и reconciliation увеличивают нагрузку на
  монолитную БД чтением WAL, контрольными запросами и построением
  контрольных сумм — на самых нагруженных доменах (Driver, Booking) это
  может временно ухудшить и без того ограниченную вертикально масштабируемую
  монолитную БД; необходимо мониторить нагрузку на монолитную PostgreSQL на
  всём протяжении миграции.
- Re-keying для Driver (поток локации) и Payments (идемпотентный ключ)
  означает, что часть исторических данных не переносится 1:1, а
  преобразуется — риск скрытых расхождений в отчётности за переходный
  период, которые сверка по мгновенному состоянию (а не по полной истории)
  может не обнаружить.
- Для денежных доменов (Payments, Payouts) требование 100%-го совпадения
  при сверке может существенно удлинить срок нахождения на этапе shadow/canary
  относительно других доменов — это осознанный компромисс в пользу
  надёжности, а не задержка ради задержки.
- Вывод старых таблиц (последний шаг пайплайна) необратим — перед ним
  обязательна проверка, что ни один компонент (включая ACL,
  Analytics/Fraud как "широкие" потребители, см.
  [02-service-map.md](02-service-map.md)) не читает более старые таблицы
  напрямую.

## Статус

Предложено.
