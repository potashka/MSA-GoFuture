# ADR-T1-05: План миграции данных из монолита в доменные сервисы

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда, data-инженеры

## Контекст

В AS-IS все 9 доменных модулей (Booking, Driver, Pricing, Payments, Payouts,
Notification, Geography, Fraud, Analytics) хранят данные в единой PostgreSQL и
обращаются к ним напрямую через SQL, пересекая границы доменов (см.
[docs/context.md](../docs/context.md)). Целевая архитектура —
Database-per-Service (требование Б4, [01-nfr.md](01-nfr.md)): у каждого
сервиса своя база (см. карту сервисов в
[02-service-map.md](02-service-map.md) и диаграмму
[c2-to-be.puml](c2-to-be.puml)).

Перенос данных должен происходить без остановки платформы и без потери
данных, при большом объёме операций (500 тыс. конкурентных поездок,
требование П1, [01-nfr.md](01-nfr.md)). Для этого используется единый
пошаговый пайплайн миграции данных, применяемый на каждом этапе декомпозиции
(см. очерёдность в [03-decomposition-order.md](03-decomposition-order.md)).

## Требования

- Нулевая потеря данных при переносе; возможность отката на любом шаге до
  момента вывода старых таблиц из эксплуатации.
- Расхождения между старой и новой моделью данных обнаруживаются
  автоматической сверкой (reconciliation) до переключения записи
  (требование С4, [01-nfr.md](01-nfr.md)).
- Для денежных потоков (Payments, Payouts) — расхождение при сверке перед
  переключением записи недопустимо (требование С2, С4,
  [01-nfr.md](01-nfr.md)): 100% совпадение обязательно.
- Миграция не должна требовать остановки записи дольше, чем допускает
  доступность соответствующего класса сервиса (Д1–Д5, [01-nfr.md](01-nfr.md)).

## Решение

### Общий пайплайн миграции (применяется к каждому сервису)

1. **CDC (Debezium)**. На таблицы монолита, принадлежащие выносимому домену,
   устанавливается коннектор Debezium, читающий WAL PostgreSQL и публикующий
   изменения в Kafka в виде потока событий изменений (см.
   [c2-to-be.puml](c2-to-be.puml): `monolithDb → cdc → kafka`).
2. **Период dual-write**. Новый доменный сервис вводится в эксплуатацию
   параллельно с монолитом: запись идёт в обе стороны — в монолитную БД (как
   и раньше) и в БД нового сервиса (синхронно из кода сервиса либо
   асинхронно через потребление CDC-потока), пока обе модели данных не
   признаны эквивалентными.
3. **Reconciliation (сверка)**. Автоматическое сравнение состояния данных
   монолита и нового сервиса (построчно, по контрольным суммам или по
   бизнес-агрегатам, в зависимости от домена) на протяжении контрольного
   периода. Критерий успеха сверки определяется индивидуально для каждого
   сервиса (см. таблицу ниже) в зависимости от цены ошибки в домене.
4. **Переключение чтения**. Читающие запросы (свои и через ACL) переводятся
   на новый сервис первыми — при обнаружении проблемы откат чтения на
   монолит не требует отмены уже принятых бизнес-решений.
5. **Переключение записи**. Только после успешной сверки и стабильного
   переключения чтения запись переводится на новый сервис как основной
   источник истины; монолит либо перестаёт писать в эти таблицы, либо
   получает данные обратным CDC-потоком (если это временно требуется другим
   ещё не мигрировавшим доменам монолита).
6. **Вывод старых таблиц**. После контрольного периода работы с записью
   исключительно в новом сервисе и подтверждения, что ни один компонент
   (включая ACL и отчётность) не читает старые таблицы, таблицы в монолитной
   БД выводятся из эксплуатации (archive + drop по регламенту хранения
   данных).

Откат возможен на шагах 1–4 без ограничений (запись всё ещё идёт и в
монолит). После шага 5 (переключение записи) откат требует явной
процедуры восстановления состояния в монолите из данных нового сервиса
(обратный CDC/экспорт) и трактуется как инцидентная, а не рутинная
операция — поэтому критерии перехода к шагу 5 (см.
[03-decomposition-order.md](03-decomposition-order.md)) должны быть особенно
строгими для денежных доменов.

### Миграция по сервисам

#### Booking

- **Таблицы**: заказы/поездки, история статусов поездки, причины отмен.
- **Стратегия**: CDC (Debezium) на всём протяжении dual-write; таблицы
  реляционные, схема переносится без смены модели ключей.
- **План отката**: до переключения записи — мгновенный (флаг возврата
  маршрута на монолит, см. [04-backward-compatibility.md](04-backward-compatibility.md));
  после переключения записи — восстановление состояния монолита из Booking
  DB через обратный экспорт, выполняется только как реакция на инцидент,
  так как Booking мигрирует последним и монолит к этому моменту уже не
  является системой записи для большинства связанных доменов (см.
  [03-decomposition-order.md](03-decomposition-order.md), этап 7).
- **Критерий успеха сверки**: 100% совпадение статусов активных
  (незавершённых) поездок в реальном времени; для завершённых/отменённых
  поездок — нулевое расхождение по контрольным суммам за скользящее окно
  не менее 7 суток перед переключением записи.

#### Driver

- **Таблицы**: профили водителей, доступность/статус, привязка к зонам —
  CDC; поток геолокации (высокочастотные обновления местоположения) —
  re-keying/переключение потока с выбранного момента времени, без переноса
  полной истории пингов.
- **Стратегия**: CDC для медленно меняющихся таблиц (профили,
  доступность); для потока локации — re-keying: новый сервис начинает
  принимать поток геособытий напрямую с момента cutover, с ограниченным
  окном backfill через CDC (для восстановления недавнего состояния), а не
  с переносом всей истории пингов (низкая долгосрочная ценность отдельных
  исторических точек локации при высоком объёме).
- **План отката**: флаг возврата на монолит; в период dual-write монолит
  продолжает принимать поток локации параллельно, чтобы откат не терял
  данные о текущей позиции водителей.
- **Критерий успеха сверки**: совпадение количества и статуса активных
  (онлайн) водителей между системами в реальном времени с расхождением не
  более значения, не влияющего на latency-бюджет П3 ([01-nfr.md](01-nfr.md));
  для исторических данных — не применяется (данные не переносятся
  полностью по стратегии re-keying).

#### Pricing

- **Таблицы**: тарифные правила, surge-коэффициенты, история котировок.
- **Стратегия**: CDC.
- **План отката**: флаг возврата на монолит до переключения записи;
  тарифные правила как конфигурация дублируются в обе системы на период
  dual-write.
- **Критерий успеха сверки**: детерминированный пересчёт выборки
  исторических котировок по тем же входным данным должен давать
  идентичный результат (нулевое расхождение) для тарифных правил;
  surge-коэффициенты, зависящие от временных окон агрегации, — расхождение
  в пределах согласованного допуска (не более одного шага
  пересчёта/окна).

#### Payments

- **Таблицы**: платёжные транзакции, платёжные методы/токены, возвраты.
- **Стратегия**: CDC + re-keying — вводится идемпотентный ключ операции
  (idempotency key), отсутствующий в схеме монолита и необходимый для
  паттерна Saga (требование С2, С3, [01-nfr.md](01-nfr.md)); существующие
  транзакции получают сгенерированный ключ поверх переносимых через CDC
  данных.
- **План отката**: до переключения записи — мгновенный, через
  feature-флаг; переключение записи выполняется только коротким окном с
  временной приостановкой новых списаний (а не "тихим" отказом), под
  контролем дежурной смены — денежный домен не допускает автоматического
  отката после реального списания без сверки на уровне транзакции.
- **Критерий успеха сверки**: 100% совпадение сумм и статусов транзакций
  между монолитом и Payments Service за весь контрольный период; любое
  расхождение блокирует переключение записи (требование С2/С4,
  [01-nfr.md](01-nfr.md)).

#### Payouts

- **Таблицы**: реестр заработка водителей, пакеты выплат, статусы
  выплатных транзакций.
- **Стратегия**: CDC.
- **План отката**: аналогично Payments — до первого реального
  выплатного пакета, обработанного новым сервисом, откат по флагу
  возможен; после этого — только через сверку баланса и ручное
  вмешательство (в т.ч. с учётом регуляторных обязательств перед
  водителями-контрагентами, требование Б3, [01-nfr.md](01-nfr.md)).
- **Критерий успеха сверки**: 100% совпадение баланса заработка каждого
  водителя (ledger balance) между системами перед переключением записи.

#### Notification

- **Таблицы**: шаблоны уведомлений, журнал доставки, пользовательские
  настройки уведомлений.
- **Стратегия**: CDC.
- **План отката**: мгновенный, флаг возврата на монолит на любом этапе —
  домен некритичен для целостности денег или поездки (пилотный этап, см.
  [03-decomposition-order.md](03-decomposition-order.md), этап 1).
- **Критерий успеха сверки**: 100% совпадение шаблонов и пользовательских
  настроек; для журнала доставки — расхождение не более допустимого лага
  доставки (не денежные данные, строгий 100%-й критерий не требуется).

#### Geography

- **Таблицы/данные**: зоны, полигоны городов, справочник геообъектов.
- **Стратегия**: snapshot + CDC — целевое хранилище (Elasticsearch)
  технологически отличается от исходной реляционной модели, поэтому
  требуется полный первичный снэпшот (bulk reindex) с последующим
  потоковым CDC для инкрементальных изменений (Debezium → Kafka Connect
  → Elasticsearch sink).
- **План отката**: чтение geosearch возвращается на монолит/его read-реплику
  через feature-флаг; ES-индекс поддерживается синхронизированным в
  течение всего периода dual-write как готовый к переключению в любой
  момент.
- **Критерий успеха сверки**: результаты геопоиска по контрольному набору
  типовых запросов (репрезентативная выборка зон/координат) совпадают
  между старым и новым хранилищем с расхождением менее согласованного
  порога (например, состав множества "ближайших/подходящих" объектов
  идентичен для не менее 99,9% контрольных запросов).

#### Fraud

- **Таблицы**: правила скоринга, чёрные списки, история инцидентов.
- **Стратегия**: CDC, с параллельным переводом источника входных данных с
  прямого SQL-доступа к другим доменам на потребление событий Kafka (см.
  [03-decomposition-order.md](03-decomposition-order.md), этап 6).
- **План отката**: флаг возврата к прежней синхронной проверке в
  монолите на период стабилизации событийной модели.
- **Критерий успеха сверки**: вердикты скоринга (решение: разрешить/
  заблокировать/эскалировать) совпадают с вердиктами монолита на
  исторической контрольной выборке операций не менее чем в согласованном
  проценте случаев (расхождения разбираются вручную перед переключением
  записи в чёрные списки).

#### Analytics

- **Данные**: в AS-IS Analytics не столько владеет обособленными
  таблицами, сколько читает данные напрямую из таблиц других доменов через
  SQL, пересекающий границы доменов (см. [docs/context.md](../docs/context.md)).
  Миграция здесь — это не перенос таблиц, а замена прямого SQL-доступа
  подпиской на события всех доменов через Kafka с построением витрин в
  ClickHouse (Spark/Flink).
- **Стратегия**: CDC как источник исторического backfill (чтобы не
  терять данные, накопленные до момента, когда домены начали публиковать
  события) + потребление событийного потока для новых данных.
- **План отката**: старые SQL-отчёты и дашборды сохраняются работающими
  параллельно с новыми витринами ClickHouse до валидации; откат — это
  возврат на старые отчёты как источник истины, без отдельного
  флага уровня Gateway (Analytics не в синхронном пути клиентских
  запросов).
- **Критерий успеха сверки**: контрольные агрегаты (суммы, количества по
  ключевым бизнес-метрикам) из новых витрин совпадают со значениями,
  посчитанными напрямую по монолитной БД, за контрольные периоды с
  расхождением, не превышающим согласованный порог (обусловленный
  задержкой доставки событий, а не потерей данных).

## Альтернативы

- **Полная одномоментная миграция данных ("big bang cutover") на каждом
  сервисе.** Отклонено: противоречит требованию минимизации простоя и
  общей стратегии Strangler Fig; не даёт времени на сверку и увеличивает
  риск необратимой потери/порчи данных при большом объёме (требование П1).
- **Snapshot без CDC (разовый перенос + периодические синхронизации).**
  Отклонено как стратегия по умолчанию: не обеспечивает актуальности
  данных при непрерывной записи в монолит в период миграции; используется
  точечно только там, где меняется сама технология хранения (Geography →
  Elasticsearch), в сочетании с последующим CDC, а не вместо него.
- **Ручная сверка вместо автоматической.** Отклонено: не масштабируется
  на объём данных (500 тыс. конкурентных поездок) и не укладывается в
  целевые сроки перехода между этапами
  ([03-decomposition-order.md](03-decomposition-order.md)).

## Компромиссы и риски

- Период dual-write увеличивает нагрузку на монолитную БД (двойная
  запись/чтение для сверки) — на самых нагруженных доменах (Driver,
  Booking) это может временно ухудшить и без того ограниченную
  вертикально масштабируемую монолитную БД; необходимо мониторить нагрузку
  на монолитную PostgreSQL на всём протяжении dual-write.
- Re-keying для Driver (поток локации) и Payments (идемпотентный ключ)
  означает, что часть исторических данных не переносится 1:1, а
  преобразуется — риск скрытых расхождений в отчётности за переходный
  период, которые сверка по мгновенному состоянию (а не по полной истории)
  может не обнаружить.
- Для денежных доменов (Payments, Payouts) требование 100%-го совпадения
  при сверке может существенно удлинить срок нахождения на этапе dual-write
  относительно других доменов — это осознанный компромисс в пользу
  надёжности, а не задержка ради задержки.
- Вывод старых таблиц (последний шаг пайплайна) необратим — перед ним
  обязательна проверка, что ни один компонент (включая ACL,
  Analytics/Fraud как "широкие" потребители, см.
  [02-service-map.md](02-service-map.md)) не читает более старые таблицы
  напрямую.

## Статус

Предложено.
