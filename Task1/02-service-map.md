# ADR-T1-02: Карта целевых сервисов (DDD bounded contexts)

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture

## Контекст

Монолит GoFuture объединяет 9 доменных модулей (Booking, Driver, Pricing,
Payments, Payouts, Notification, Geography, Analytics, Fraud) вокруг одной
PostgreSQL, к которой все модули обращаются напрямую через SQL, пересекая
границы доменов (см. [docs/context.md](../docs/context.md)). Целевая
архитектура — набор независимых доменных сервисов по границам, определённым
через DDD (bounded context), с изоляцией данных (Database-per-Service) и
явными контрактами взаимодействия (события через Kafka, синхронные API там,
где это необходимо бизнес-логике).

Организационно за доменами стоят 8 продуктовых команд на 9 доменных модулей
(см. [docs/context.md](../docs/context.md)). Payments и Payouts выделены как
раздельные bounded context и раздельные сервисы (разные регуляторные
требования и SLA — Payments работает в реальном времени в цепочке поездки,
Payouts — это, по сути, отложенный расчётный/бухгалтерский процесс), но
закреплены за одной продуктовой командой (Payments & Payouts team), что и
закрывает разрыв "8 команд / 9 доменов".

## Требования

- Каждый сервис должен однозначно принадлежать одному bounded context и
  одной владеющей команде (границы сервиса = границы команды, по аналогии с
  законом Конвея).
- Каждый сервис владеет собственными данными; доступ к ним извне — только
  через API или события, без прямого SQL через границу домена (требование
  Б4, [01-nfr.md](01-nfr.md)).
- Взаимодействие между сервисами по умолчанию асинхронное через события
  (требование С1, [01-nfr.md](01-nfr.md)); синхронные вызовы — только там,
  где бизнес-процесс требует немедленного ответа в рамках latency-бюджетов
  П2–П4.
- Платформенные возможности (маршрутизация, аутентификация/авторизация),
  общие для всех доменов, выносятся в отдельные платформенные сервисы, а не
  дублируются в каждом домене.

## Решение

### Доменные сервисы

#### Booking

- **Bounded context**: приём заказа поездки, управление её жизненным циклом
  (создание → подтверждение → в пути → завершение/отмена). Оркестрирует
  вызовы к Pricing, Driver, Payments, Fraud в рамках одного заказа.
- **Владеющая команда**: Booking team.
- **Собственные данные**: заказы (поездки), история статусов поездки,
  причины отмен.
- **Публикуемые события**: `BookingCreated`, `BookingConfirmed`,
  `BookingCancelled`, `TripStarted`, `TripCompleted`.
- **Потребляемые события**: `DriverMatched` (Driver), `PriceQuoted`
  (Pricing), `PaymentAuthorized` / `PaymentFailed` (Payments),
  `FraudCheckResult` (Fraud).
- **Синхронные API**: `CreateBooking`, `GetBookingStatus`, `CancelBooking`
  (через API Gateway для клиентов); синхронный вызов Pricing за котировкой и
  Driver за матчингом в рамках создания заказа (latency-бюджет П2).

#### Driver

- **Bounded context**: состояние и местоположение водителей, доступность,
  подбор ("умное" перераспределение вместо ближайшего водителя), борьба с
  "горячими зонами" совместно с Geography.
- **Владеющая команда**: Driver team.
- **Собственные данные**: профили водителей, текущая локация и статус,
  доступность, история назначений.
- **Публикуемые события**: `DriverLocationUpdated`, `DriverMatched`,
  `DriverAvailabilityChanged`.
- **Потребляемые события**: `BookingCreated` (инициирует матчинг),
  `TripCompleted` / `BookingCancelled` (освобождение водителя),
  `HotZoneDetected` / `ZoneDemandUpdated` (Geography, для логики
  перераспределения).
- **Синхронные API**: высокочастотный приём геолокации (латентность П3),
  `RequestMatch` (синхронный вызов из Booking), `GetDriverStatus`.

#### Pricing

- **Bounded context**: динамическое ценообразование поездки в реальном
  времени, тарифные правила, surge-коэффициенты.
- **Владеющая команда**: Pricing team.
- **Собственные данные**: тарифные правила, surge-коэффициенты, история
  котировок.
- **Публикуемые события**: `PriceQuoted`, `SurgeZoneUpdated`.
- **Потребляемые события**: `HotZoneDetected` / `ZoneDemandUpdated`
  (Geography — сигнал спроса), `DriverAvailabilityChanged` (Driver — сигнал
  предложения).
- **Синхронные API**: `CalculatePrice` / `GetQuote` (синхронный вызов из
  Booking, latency-бюджет П4).

#### Payments

- **Bounded context**: авторизация и списание платежа за поездку,
  взаимодействие с внешними платёжными провайдерами.
- **Владеющая команда**: Payments & Payouts team.
- **Собственные данные**: платёжные транзакции, статусы
  авторизации/списания, платёжные токены.
- **Публикуемые события**: `PaymentAuthorized`, `PaymentCaptured`,
  `PaymentFailed`, `PaymentRefunded`.
- **Потребляемые события**: `TripCompleted` (инициирует списание),
  `BookingCancelled` (отмена авторизации/возврат).
- **Синхронные API**: `AuthorizePayment`, `CapturePayment`, `RefundPayment`;
  интеграция с Яндекс Пэй и API банков.

#### Payouts

- **Bounded context**: расчёт заработка и выплаты водителям; отдельный
  bounded context от Payments из-за иных регуляторных требований
  (бухгалтерские/налоговые обязательства перед водителями-контрагентами) и
  иного SLA (пакетный/отложенный процесс, а не синхронная операция в
  цепочке поездки).
- **Владеющая команда**: Payments & Payouts team.
- **Собственные данные**: реестр заработка водителей, пакеты выплат,
  статусы выплатных транзакций.
- **Публикуемые события**: `PayoutInitiated`, `PayoutCompleted`,
  `PayoutFailed`.
- **Потребляемые события**: `PaymentCaptured` / `TripCompleted` (начисление
  заработка водителю).
- **Синхронные API**: `GetDriverBalance`, `InitiatePayout` (в т.ч. по
  расписанию/из админ-панели); интеграция с API банков.

#### Notification

- **Bounded context**: доставка уведомлений пассажирам и водителям (push,
  и др. каналы).
- **Владеющая команда**: Notification team.
- **Собственные данные**: шаблоны уведомлений, журнал доставки, статусы
  доставки, пользовательские настройки уведомлений.
- **Публикуемые события**: `NotificationSent`, `NotificationFailed`.
- **Потребляемые события**: практически весь поток доменных событий
  (`BookingConfirmed`, `DriverMatched`, `PaymentFailed`, `PayoutCompleted` и
  т. д.) — сервис является потребителем-агрегатором событий.
- **Синхронные API**: минимальные, преимущественно административные
  (управление шаблонами); исходящая интеграция с FCM, APNs, Huawei Push Kit.

#### Geography

- **Bounded context**: геопоиск, зоны, картографические данные, детекция
  зон повышенного спроса ("горячих зон").
- **Владеющая команда**: Geography team.
- **Собственные данные**: геоиндекс (Elasticsearch), полигоны зон/городов,
  карта спроса.
- **Публикуемые события**: `HotZoneDetected`, `ZoneDemandUpdated`,
  `GeofenceEvent`.
- **Потребляемые события**: `DriverLocationUpdated` (Driver — агрегация
  плотности водителей по зонам).
- **Синхронные API**: `GeoSearch` (ближайшие/подходящие объекты),
  маршрутизация; интеграция с Яндекс Картами.

#### Fraud

- **Bounded context**: обнаружение мошеннических паттернов (фиктивные
  поездки, платёжные махинации, сговор водитель-пассажир).
- **Владеющая команда**: Fraud team.
- **Собственные данные**: модели риск-скоринга, чёрные списки, история
  инцидентов.
- **Публикуемые события**: `FraudCheckResult`, `FraudAlertRaised`.
- **Потребляемые события**: широкий поток доменных событий
  (`BookingCreated`, `PaymentAuthorized`, `DriverLocationUpdated` и др.) —
  целевая модель полностью событийная (см.
  [03-decomposition-order.md](03-decomposition-order.md), этап 6), в
  отличие от AS-IS, где Fraud вызывается синхронно в цепочке Booking.
- **Синхронные API**: точечные блокирующие проверки high-risk операций при
  необходимости; основной режим — асинхронный.

#### Analytics

- **Bounded context**: агрегация и анализ операционных и бизнес-метрик в
  реальном времени и в ретроспективе.
- **Владеющая команда**: data-инженеры.
- **Собственные данные**: витрины и агрегаты в ClickHouse.
- **Публикуемые события**: как правило, не публикует доменные события
  (терминальный потребитель); может публиковать служебные
  `AnalyticsAlertRaised` для операционного мониторинга бизнес-метрик.
- **Потребляемые события**: весь поток доменных событий через Kafka,
  обрабатываемый Spark/Flink для построения витрин, отображаемых в
  DataLens.
- **Синхронные API**: только для чтения (внутренние потребители отчётов).

### Платформенные сервисы

#### API Gateway

- **Bounded context**: единая точка входа для клиентов; маршрутизация,
  версионирование API, feature flags, постепенное переключение трафика
  между монолитом и доменными сервисами.
- **Владеющая команда**: платформенная команда.
- **Собственные данные**: конфигурация маршрутизации, feature-флаги,
  версии API (без доменных данных).
- **Публикуемые/потребляемые события**: не участвует в доменной событийной
  шине; работает на уровне синхронных вызовов.
- **Синхронные API**: единая точка входа для мобильных приложений,
  веб-портала и админ-панели.

#### Identity Service

- **Bounded context**: аутентификация и авторизация пассажиров, водителей,
  сотрудников; управление ролями и доступами (IAM).
- **Владеющая команда**: платформенная команда.
- **Собственные данные**: учётные записи, роли, разрешения, сессии/токены.
- **Публикуемые события**: `UserAuthenticated` / `AccountLocked` (для
  аудита, потребляется Fraud/Analytics при необходимости).
- **Потребляемые события**: минимально.
- **Синхронные API**: `Authenticate`, `ValidateToken`, `Authorize` —
  используется всеми сервисами и API Gateway через mTLS.

## Альтернативы

- **Объединить Payments и Payouts в один сервис.** Отклонено: разные
  регуляторные требования (расчёты с пассажирами vs. выплаты
  водителям-контрагентам) и разные SLA (синхронный реального времени vs.
  пакетный) делают общий bounded context нарушением принципа единственной
  ответственности и усложняют независимое масштабирование и деплой.
- **Считать Fraud и Analytics частью инфраструктуры наблюдаемости, а не
  доменными сервисами.** Отклонено: обе системы инкапсулируют доменную
  бизнес-логику (правила скоринга риска, бизнес-метрики) и владеют
  собственными данными — это доменные bounded context, а не сквозная
  инфраструктура.
- **Не выделять Identity Service отдельно, оставить аутентификацию в API
  Gateway.** Отклонено: аутентификация/авторизация — самостоятельный
  bounded context с собственным жизненным циклом данных (учётные записи,
  роли), который переиспользуется не только Gateway, но и
  сервис-сервисным взаимодействием (mTLS/IAM, требование Б1–Б2).

## Компромиссы и риски

- Fraud и Notification как "потребители всего потока событий" создают
  широкую неявную связанность через схему событий: изменение формата
  события в любом домене может затронуть оба сервиса — требуется
  версионирование схем событий и contract-тесты (см.
  [04-backward-compatibility.md](04-backward-compatibility.md)).
- Разделение Payments/Payouts в рамках одной команды снижает
  организационный риск (нет борьбы за приоритеты между командами), но
  сохраняет риск того, что команда де-факто продолжит проектировать их как
  один модуль — необходимо явно поддерживать раздельные БД и контракты.
- Booking как оркестратор синхронных вызовов (Pricing, Driver, Payments,
  Fraud) остаётся точкой потенциальных каскадных отказов и после
  декомпозиции, если не внедрить таймауты/circuit breaker — те же
  архитектурные риски, что и в монолите, но теперь на уровне сети, а не
  вызовов в одном процессе.
- Analytics зависит от полноты и своевременности событий всех остальных
  доменов; на переходном периоде (пока часть доменов ещё в монолите и
  данные приходят через CDC, см. [05-data-migration-plan.md](05-data-migration-plan.md))
  возможны пробелы и задержки в витринах.

## Статус

Предложено.
