# ADR-T3-02: Стратегия репликации данных

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда, SRE

## Контекст

С выбором 4 регионов (`sgp`, `jkt`, `sao`, `core`, см.
[01-region-selection.md](01-region-selection.md)) нужно зафиксировать, какие
данные живут только в своём регионе, какие реплицируются глобально, и как
устроена репликация внутри региона между зонами доступности — под целевую
доступность 99,99% для Tier-1 ride APIs в Task3 и latency-бюджеты П2–П4
([Task1/01-nfr.md](../Task1/01-nfr.md)). Каждый доменный сервис уже владеет
собственной БД (Database-per-Service, [Task1/02-service-map.md](../Task1/02-service-map.md)),
а Kafka развёрнута по одному кластеру на регион
([Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)).

## Требования

- Latency-бюджеты П2–П4 ([Task1/01-nfr.md](../Task1/01-nfr.md)) физически
  недостижимы при синхронных вызовах между удалёнными континентами
  (Сингапур/Джакарта ↔ Сан-Паулу — межконтинентальная задержка порядка
  сотен миллисекунд в одну сторону, на два порядка больше всего бюджета П2)
  — данные и обработка "горячего" пути поездки должны находиться в одном
  регионе.
- Для персональных, платёжных и точных операционных данных действует
  консервативное архитектурное допущение: они остаются в исходной
  юрисдикции/регионе, а cross-border transfer разрешается только после
  юридической квалификации и настройки допустимого механизма
  ([05-compliance.md](05-compliance.md)).
- RTO/RPO по классам сервисов (Д3–Д5, [Task1/01-nfr.md](../Task1/01-nfr.md))
  должны выполняться при отказе одной зоны доступности без вмешательства
  человека.
- Справочные данные, конфигурация и общая идентификация пользователя
  (IAM) должны быть согласованы во всех регионах без необходимости
  синхронного обращения в другой регион на каждый запрос.

## Решение

### Принцип: региональный шардинг вместо глобальной репликации

Данные поездок, локаций водителей и платежей **живут только в своём
регионе поездки (`ride_region`)** — регионе, где оказывается услуга и
где находятся локальная карта, водители, тарифы, Fraud realtime и
платёжный адаптер (см. [03-geo-routing.md](03-geo-routing.md)). Этот
регион определяется для конкретного `CreateBooking` по точке посадки,
выбранному городу, tenant/market и конфигурации приложения, а не по
региону хранения профиля пассажира. Эти данные не реплицируются в другие
страны/юридические зоны в hot path; DR-репликация допускается только в
рамках [05-compliance.md](05-compliance.md) и [04-failover.md](04-failover.md):

- Booking DB, Driver DB, Pricing DB, Payments DB, Payouts DB, Fraud DB,
  Geography DB (см. [Task1/02-service-map.md](../Task1/02-service-map.md))
  — по одному независимому набору на регион (`sgp`, `jkt`, `sao`), плюс
  такой же набор для трафика, обслуживаемого из `core` (если домашний
  регион также обслуживает поездки, а не только админку — в противном
  случае этот набор в `core` не нужен).
- Региональные Kafka-кластеры и их топики (`sgp.*`, `jkt.*`, `sao.*`, см.
  [Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)) — данные саги
  поездки в базовой модели остаются в Kafka-кластере своего региона.

Это одновременно решает задачу latency (данные и обработка соседствуют) и
задачу data residency/cross-border risk (чувствительные данные по
умолчанию остаются в регионе/юрисдикции) одним и тем же архитектурным
решением, а не двумя разными механизмами.

### Что реплицируется глобально (асинхронно)

Только данные, для которых существует единственный глобальный источник
правды и которые не являются частью "горячего" транзакционного пути
поездки:

- **Справочники**: шаблоны уведомлений ([Task2/01-domain-events.md](../Task2/01-domain-events.md)
  — `NotificationRequested.template_code`), справочники правил
  Fraud-скоринга без привязки к конкретному инциденту, справочники
  тарифных схем (структура тарифа, не сами surge-коэффициенты — те
  региональны и оперативны).
- **Конфигурация**: канонические схемы Schema Registry
  ([Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)), feature-флаги
  платформы, конфигурация маршрутизации API Gateway.
- **Профили**: только тонкий глобальный индекс — глобальный идентификатор
  пользователя/водителя и указатель на его `profile_region` (регион
  хранения профиля, см. [03-geo-routing.md](03-geo-routing.md)). Персональные
  данные профиля (имя, телефон, платёжные методы, история поездок)
  остаются в региональной БД `profile_region` и не входят в этот
  глобально реплицируемый индекс. Это консервативное архитектурное
  допущение до подтверждения местного юриста; в этом ADR
  "профили" означает указатель, а не содержимое.
- **IAM**: Identity Service ведёт глобальный каталог учётных записей
  (существование пользователя, роль, `profile_region`), реплицируемый во
  все регионы асинхронно, чтобы аутентификация могла выполняться в любом
  регионе без синхронного обращения в `core` на каждый запрос (см.
  [03-geo-routing.md](03-geo-routing.md)); сами секреты/пароли — хешированы
  и также реплицируются как часть этого каталога (хеш, не открытый пароль).

Асинхронная репликация означает eventual consistency с задержкой в
секунды-минуты — приемлемо, так как эти данные не находятся на пути
завершения конкретной поездки и меняются нечасто относительно потока
`Booking*`/`Driver*` событий.

### Репликация внутри региона (между зонами доступности)

Каждый регион (`sgp`, `jkt`, `sao`, `core`) разворачивается на 3 зонах
доступности (требование к выбору региона, см.
[01-region-selection.md](01-region-selection.md)):

- **PostgreSQL**: синхронная репликация между зонами доступности (managed
  multi-AZ на базе PostgreSQL RDS — уже часть стека компании, см.
  [docs/context.md](../docs/context.md)) — первичный узел в одной зоне,
  минимум один синхронный standby в другой зоне (`synchronous_commit` до
  подтверждения записи хотя бы одной репликой вне зоны первичного узла).
  При отказе зоны с первичным узлом происходит promotion sync/semisync
  standby. Перед открытием записи на новом primary обязательно выполняется
  fencing старого primary (managed DB lease, cloud detach/stop или
  STONITH), чтобы исключить split-brain. RPO зависит от режима:
  `synchronous_commit` даёт RPO 0 для подтверждённых транзакций внутри
  региона; semisynchronous режим допускает RPO до 1 минуты, что
  соответствует Tier-1 целям из [04-failover.md](04-failover.md).
- **Kafka**: RF=3 по зонам доступности — каждый брокер помечен зоной
  (rack-awareness), партиции размещаются так, что все 3 реплики партиции
  находятся в разных зонах; `min.insync.replicas=2` (уже зафиксировано в
  [Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)) и producer
  `acks=all` задают RPO 0 для подтверждённых сообщений при отказе одного
  брокера/AZ. Неподтверждённые produce-запросы повторяются идемпотентно.
  Для Tier-1 топиков запрещён unclean leader election.
- **Доменные сервисы**: без сохраняемого состояния в самом сервисе
  (Kubernetes, поды распределены по 3 зонам) — отказ зоны не требует
  специальной репликации, только перераспределения реплик пода (см.
  [04-failover.md](04-failover.md)).
- **Redis/cache**: Redis используется как cache/read model acceleration и
  не является источником истины. Потеря Redis допустима как потеря кэша:
  данные восстанавливаются из PostgreSQL, Kafka или материализованных
  read models; RPO для бизнес-данных при отказе Redis не применяется.

### Межрегиональная репликация и DR

Межрегиональная репликация разрешена только для данных, которые прошли
классификацию и не выходят за рамки residency/cross-border policy из
[05-compliance.md](05-compliance.md):

- справочники, конфигурация, схемы и feature flags;
- тонкий IAM-индекс (`user_id`, `tenant_id`, `profile_region`, роли без PII);
- разрешённые read-only profile projections по allowlist;
- агрегированные/анонимизированные аналитические витрины;
- DR-копии операционных данных только внутри той же юридической зоны или
  при заранее подтверждённом юридическом основании и настроенном
  допустимом механизме передачи.

Для Kafka разрешённые межрегиональные потоки реплицируются через
MirrorMaker 2 или аналог. RPO таких потоков равен фактическому replication
lag; целевое значение для DR-потоков Tier-1 — ≤ 5 минут, для глобальных
аналитических/справочных потоков — ≤ 15 минут. Асинхронная
межрегиональная репликация не описывается как RPO 0: при disaster
возможна потеря событий в пределах lag, и это
учитывается runbook/reconciliation.

PostgreSQL cross-region replication применяется только для разрешённых
данных и только асинхронно. Promotion DR-replica требует fencing старого
primary и явного объявления нового writer, иначе есть риск split-brain и
двух источников записи для одного `ride_region`.

Диаграмма: [replication-schema.puml](replication-schema.puml).

## Альтернативы

- **Active-active глобальная репликация данных поездок/платежей между
  всеми регionami.** Отклонено:
  - **Latency**: синхронная репликация, необходимая для строгой
    консистентности active-active, потребовала бы межконтинентальных
    round-trip (`sgp`/`jkt` ↔ `sao`) порядка сотен миллисекунд — на два
    порядка превышает latency-бюджеты П2–П4
    ([Task1/01-nfr.md](../Task1/01-nfr.md)).
  - **Data residency/cross-border risk**: active-active подразумевает
    копии чувствительных данных в каждом регионе кластера. Без
    юридической квалификации, подтверждения местного юриста и
    допустимого механизма передачи это противоречит консервативной
    policy из [05-compliance.md](05-compliance.md).
  - **Конфликты записи в денежных потоках**: active-active потребовал бы
    механизма разрешения конфликтов при параллельной записи в одну и ту же
    запись из разных регионов — для Payments/Payouts (требование С2/С3,
    [Task1/01-nfr.md](../Task1/01-nfr.md)) это создаёт риск двойного
    списания/начисления, требующий сложных CRDT/распределённого консенсуса
    поверх и без того сложной Saga ([Task2/04-saga.md](../Task2/04-saga.md)).
  - **Несоответствие паттерну доступа**: ни одна поездка не читается и не
    пишется из другого региона, кроме своего собственного — active-active
    решает проблему многорегионального конкурентного доступа к одним и тем
    же данным, которой у GoFuture нет; региональный шардинг проще и точнее
    соответствует реальному паттерну доступа.
- **Глобальная синхронная репликация только для Payments (как наиболее
  критичного домена), при региональном шардинге остальных.** Отклонено:
  Payments не читается/не пишется из другого региона чаще, чем любой
  другой домен саги ([Task2/04-saga.md](../Task2/04-saga.md)) — выделение
  Payments как исключения добавило бы сложность ради несуществующей
  выгоды и создало бы единственную точку, нарушающую принцип
  "региональный шардинг = latency + резидентность одним решением".
- **Полная репликация профиля пользователя (включая PII) глобально для
  ускорения "холодного старта" в роуминге.** Отклонено как базовая модель: увеличивает масштаб последствий утечки данных и требует отдельной юридической квалификации для каждого рынка. Вместо этого роуминг реализуется на уровне маршрутизации: `profile_region` используется для профиля, `ride_region` — для конкретной поездки, а также применяются token claims и локальная read-only projection, см.
  [03-geo-routing.md](03-geo-routing.md).

## Компромиссы и риски

- Аналитика, требующая глобального среза (Analytics Service,
  [Task1/02-service-map.md](../Task1/02-service-map.md)), не может просто
  читать сырые события из всех регионов напрямую — требуется отдельный
  процесс агрегированного/анонимизированного экспорта витрин в общее
  хранилище, не являющийся частью репликации из этого документа (этот риск
  уже отмечен в [Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)).
- Пользователь, оказавшийся вне `profile_region` (роуминг), может получить
  дополнительный hop или redirect только на этапе входа. После определения
  `ride_region` активная поездка обслуживается локально в регионе оказания
  услуги, без прямого обращения в БД профиля на каждый location update
  (см. [03-geo-routing.md](03-geo-routing.md)).
- Синхронная репликация PostgreSQL между зонами добавляет latency записи
  (подтверждение от удалённой зоны) по сравнению с записью в одну зону —
  осознанный компромисс ради RPO ≈ 0 при отказе зоны (Tier 1, Д3,
  [Task1/01-nfr.md](../Task1/01-nfr.md)); величина накладных расходов
  зависит от сетевой связности между зонами конкретного провайдера и
  должна быть измерена при выборе провайдера региона.
- Тонкий глобальный IAM-индекс (глобальный ID + `profile_region`) всё ещё
  требует согласования схемы между всеми регионами при любом изменении —
  подчиняется тем же принципам эволюции схем через Schema Registry
  (BACKWARD), что и доменные события ([Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)).
