# ADR-T3-01: Выбор регионов глобального развёртывания

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, инфраструктурная команда

## Контекст

Бизнес-требование — горизонтальное масштабирование в 3+ географических
регионах, включая Юго-Восточную Азию и Южную Америку (требование М2,
[Task1/01-nfr.md](../Task1/01-nfr.md); [docs/context.md](../docs/context.md)).
Task2 зафиксировал региональную модель на уровне именования Kafka-топиков
(`{region}.{domain}.{event}`, с примерами `sea`/`sam`/`core`, см.
[Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md)), но не выбирал
конкретные города/регионы. Этот документ фиксирует конкретный выбор.

Дополнительное требование этой задачи — **99,99% доступности** для
глобального развёртывания и низкая задержка в Юго-Восточной Азии и Южной
Америке. Это выше, чем целевые 99,95% для критических сервисов (Д1,
[Task1/01-nfr.md](../Task1/01-nfr.md)), зафиксированные ранее. Эта работа
трактует 99,99% как целевой показатель доступности **инфраструктурного
слоя** (регион + зоны доступности + failover, см.
[04-failover.md](04-failover.md)) для критического пути (Tier 1: Booking,
Driver, Pricing, Payments, API Gateway, Identity) — то есть более строгую
инфраструктурную планку, которую качественный дизайн региона/зон делает
достижимой сверх минимума, зафиксированного в Task1. Рекомендуется
синхронизировать [Task1/01-nfr.md](../Task1/01-nfr.md) (Д1) с этим более
строгим показателем для Tier 1 по итогам данной серии ADR; для Tier 2/3
показатели Task1 (99,9%) не пересматриваются — их отставание от Tier 1
обосновано ранее и не связано с региональным дизайном.

## Требования

- **Близость к пользователям (latency)**: регион должен обеспечивать
  латентность в рамках бюджетов П2–П4 ([Task1/01-nfr.md](../Task1/01-nfr.md))
  для основной массы пользователей соответствующего рынка.
- **3+ зоны доступности**: у выбранного облачного провайдера в городе/метро
  должно быть не менее 3 независимых зон доступности — основа для
  синхронной репликации PostgreSQL и Kafka RF=3 по зонам (требование М1,
  [Task1/01-nfr.md](../Task1/01-nfr.md); см. [02-replication.md](02-replication.md)).
- **Регуляторные требования data residency**: персональные и регуляторно
  значимые данные не должны покидать юрисдикцию, где это требуется законом
  (требование Б3, [Task1/01-nfr.md](../Task1/01-nfr.md)).
- **Стоимость**: инфраструктурные затраты должны быть соразмерны размеру
  рынка и не быть единственным решающим фактором там, где регуляторное
  требование императивно.

## Решение

Выбраны **4 региона**:

| Регион (код) | Город | Роль | Ключевое основание |
|---|---|---|---|
| `sgp` | Сингапур | Сетевой хаб Юго-Восточной Азии | Крупный узел подводных магистральных кабелей и пиринга ЮВА — низкая латентность до большинства стран региона (кроме Индонезии, где решающим фактором является требование резидентности, а не одна лишь latency); зрелый рынок облачных провайдеров с 3+ независимыми зонами доступности |
| `jkt` | Джакарта | Индонезия — крупнейший рынок ЮВА | Требование локализации персональных данных по UU PDP (закон Индонезии о защите персональных данных) — обслуживание индонезийских пользователей требует хранения и обработки их данных в индонезийской юрисдикции независимо от того, что Сингапур ближе как сетевой хаб |
| `sao` | Сан-Паулу | Бразилия — основной рынок Южной Америки | Крупнейший экономический центр Южной Америки, лучшая связность региона; требование LGPD (бразильский закон о защите персональных данных) по резидентности данных бразильских пользователей |
| `core` | Домашний регион (существующая инфраструктура Yandex Cloud, см. [docs/context.md](../docs/context.md)) | Админ-панель, глобальные сервисы | Уже эксплуатируется; не обслуживает трафик поездок напрямую, хранит только то, что по определению глобально (см. [02-replication.md](02-replication.md)) |

Это уточняет региональную модель [Task2/02-kafka-topics.md](../Task2/02-kafka-topics.md):
условное обозначение `sea`, использованное там как пример, заменяется двумя
конкретными регионами `sgp` и `jkt` (Юго-Восточная Азия обслуживается двумя
независимыми регионами по разным причинам — сетевой хаб и регуляторное
требование, а не один общий регион), `sam` конкретизируется как `sao`.
Итоговый набор кодов регионов: `sgp`, `jkt`, `sao`, `core` — 4 региона,
что покрывает требование М2 (3+ региона) с запасом.

### Обоснование по критериям

- **Latency**: `sgp` покрывает основную часть трафика ЮВА вне Индонезии с
  минимальными задержками благодаря сетевому хабу; `jkt` даёт локальную
  обработку для крупнейшего рынка региона; `sao` — основной хаб связности
  Южной Америки.
- **3+ зоны доступности**: `sgp` и `sao` — зрелые облачные рынки, где
  крупные провайдеры предоставляют 3+ независимые зоны. Для `jkt` наличие
  3+ зон доступности у выбранного провайдера должно быть подтверждено на
  этапе закупки инфраструктуры (см. риск ниже) — это развивающийся, но
  быстро растущий облачный рынок.
- **Data residency**: `jkt` и `sao` выбраны прежде всего по этому критерию
  — соответствующие юрисдикции требуют локальной обработки персональных
  данных своих граждан (см. [05-compliance.md](05-compliance.md)).
- **Стоимость**: `sgp` и `sao` — экономически обоснованный выбор (развитые
  рынки с конкуренцией облачных провайдеров); `jkt` — затраты приняты как
  необходимые для соответствия регуляторным требованиям, а не как
  оптимизация стоимости.

### Провайдер облачной инфраструктуры по регионам

Существующий стек компании использует Yandex Cloud ([docs/context.md](../docs/context.md)),
эксплуatируемый в домашнем регионе (`core`). У Yandex Cloud нет
опубликованных зон доступности в Сингапуре, Джакарте или Сан-Паулу —
поэтому для `sgp`, `jkt`, `sao` требуется отдельный облачный
провайдер(-ы) с реальным присутствием (3+ зоны доступности) в этих
городах. Конкретный выбор провайдера для новых регионов — решение вне
архитектурного скоупа (закупочный процесс инфраструктурной команды);
архитектурное требование к нему — соответствие тем же 4 критериям выше,
независимо от бренда.

## Альтернативы

- **Куала-Лумпур (Малайзия) вместо Сингапура как хаб ЮВА.** Рассмотрено:
  географически близок к Сингапуру, потенциально дешевле. Отклонено как
  основной хаб: Сингапур остаётся основным узлом магистральной связности
  региона (лучший пиринг/latency к большинству стран ЮВА) и более зрелым
  рынком облачных провайдеров с гарантированными 3+ зонами доступности;
  Куала-Лумпур может быть рассмотрен в будущем как дополнительный регион,
  если возникнет малайзийское регуляторное требование резидентности данных
  (на текущий момент такое требование не зафиксировано в
  [docs/context.md](../docs/context.md)).
- **Богота (Колумбия) вместо Сан-Паулу как хаб Южной Америки.** Рассмотрено:
  центральное положение для испаноязычной части Латинской Америки (Колумбия,
  Перу, Эквадор и др.). Отклонено как основной регион: Сан-Паулу
  представляет наибольший отдельный рынок (Бразилия) с собственным явным
  регуляторным основанием (LGPD) и более развитой облачной/сетевой
  инфраструктурой Южной Америки в целом; Богота остаётся кандидатом на
  будущее расширение при росте испаноязычного трафика LATAM, но не
  требуется для выполнения текущего требования "3+ региона" (оно уже
  выполнено выбранными 4 регионами).
- **Один общий регион ЮВА (например, только Сингапур) без отдельного
  Джакарта.** Отклонено: не удовлетворяет требованию резидентности данных
  UU PDP для индонезийских пользователей — крупнейший рынок региона
  ([docs/context.md](../docs/context.md) явно упоминает Юго-Восточную Азию
  как целевой регион, а Индонезия — его крупнейший рынок по условию этой
  задачи) не может обслуживаться из юрисдикции, не соответствующей
  локальному закону.

## Компромиссы и риски

- Наличие 3+ зон доступности в Джакарте у конкретного провайдера должно
  быть подтверждено на этапе закупки — если у выбранного провайдера меньше
  зон, потребуется либо гибридное решение (например, 2 зоны + компенsирующий
  механизм на уровне приложения), либо выбор другого провайдера/локации в
  пределах Индонезии, удовлетворяющей UU PDP.
- Разделение ЮВА на два региона (`sgp` и `jkt`) увеличивает операционную
  сложность (два независимых Kafka-кластера, две БД-инфраструктуры вместо
  одной для региона) по сравнению с моделью "один регион на континент" —
  это осознанный компромисс ради соответствия регуляторным требованиям, а
  не издержка, которую можно устранить.
- Отсутствие присутствия Yandex Cloud в новых регионах означает, что
  компания эксплуатирует более одного облачного провайдера одновременно —
  увеличивает разнообразие операционных практик (IaC, мониторинг,
  управление доступом) для инфраструктурной команды; требует единого слоя
  абстракции (Kubernetes как общий знаменатель, уже принятый как
  оркестратор) поверх разных провайдеров.
- Целевой показатель 99,99% для инфраструктурного слоя Tier 1 — цель,
  которую ещё предстоит подтвердить фактическим SLA выбранных облачных
  провайдеров по каждому региону; конкретные договорные SLA провайдеров
  могут не давать 99,99% "из коробки" на уровне отдельного региона без
  дополнительного мультизонального дизайна (см. [04-failover.md](04-failover.md)).
