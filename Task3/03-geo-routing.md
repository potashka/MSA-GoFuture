# ADR-T3-03: Механизм геомаршрутизации

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда

## Контекст

При региональном шардинге ([02-replication.md](02-replication.md)) данные
конкретного пользователя (пассажира или водителя) физически существуют
только в одном регионе — его домашнем регионе. Запрос от клиентского
приложения должен быть направлен именно в этот регион, а не просто в
географически ближайший дата-центр, иначе он не найдёт данные пользователя.
Одновременно нужно обеспечить минимальную задержку первого соединения
(требование П2, [Task1/01-nfr.md](../Task1/01-nfr.md)) и устойчивость входной
точки к отказу целого региона (см. [04-failover.md](04-failover.md)).

## Требования

- Первое соединение клиента должно устанавливаться с минимальной задержкой
  — маршрутизация должна учитывать сетевую близость, а не только
  DNS-геолокацию по IP (которая может быть неточной, например, для
  мобильных операторов с централизованным NAT).
- Запрос авторизованного пользователя должен в итоге обрабатываться его
  домашним регионом (где физически лежат его данные, см.
  [02-replication.md](02-replication.md)), даже если ближайшая по сети
  точка входа — другой регион (роуминг).
- Отказ целого региона должен приводить к перенаправлению нового трафика на
  другой регион на сетевом уровне без ожидания истечения TTL DNS-записей
  (см. [04-failover.md](04-failover.md)).
- Поездка, начавшаяся рядом с границей между зонами обслуживания регионов
  (например, паромный маршрут Сингапур — Батам/Индонезия), не должна
  требовать межрегиональной синхронной координации в процессе самой
  поездки.

## Решение

### 1. GeoDNS + latency-based routing

DNS-имя API Gateway резолвится в адрес ближайшего по сети региона:
GeoDNS определяет исходный регион клиента по IP, а latency-based
политика (там, где провайдер DNS её поддерживает) уточняет выбор по
фактически измеренной задержке до кандидатов, а не только по
географической близости "по прямой" — учитывает реальные пиринговые
маршруты (важно для случаев вроде Джакарты, где Сингапур физически ближе
некоторым пользователям, чем `jkt`, но не является их домашним регионом по
регуляторным причинам, см. [01-region-selection.md](01-region-selection.md)).
Результат этого шага — быстрое попадание на **какой-то** близкий регион,
не обязательно домашний регион пользователя.

### 2. Anycast для API Gateway

Публичный IP-адрес API Gateway анонсируется по BGP (anycast) из всех 4
регионов одновременно. Сеть маршрутизирует пакет клиента к топологически
ближайшему анонсирующему региону автоматически, на сетевом уровне — без
участия DNS вообще. Это даёт два эффекта: дополнительный (к GeoDNS)
уровень приближения точки входа к клиенту, и, что важнее для аварийного
переключения ([04-failover.md](04-failover.md)), при отказе региона его
anycast-анонс отзывается (withdraw) и трафик автоматически перетекает к
следующему ближайшему региону без ожидания истечения TTL DNS-записей —
GeoDNS этого свойства сам по себе не даёт.

### 3. Region affinity в токене

При регистрации/первой аутентификации пользователю (пассажиру или
водителю) назначается домашний регион — регион, где будет создана и будет
жить его запись профиля (см. [02-replication.md](02-replication.md)).
Identity Service включает это значение как claim в выданный токен, например
`home_region: jkt`. Все последующие запросы несут этот токен.

Точка входа (см. п. 1–2), на которую GeoDNS/anycast привели запрос,
проверяет claim `home_region` в токене:

- Если `home_region` совпадает с регионом точки входа — запрос
  обрабатывается локально, без дополнительных прыжков.
- Если не совпадает (пользователь в роуминге — например, индонезийский
  пассажир физически рядом с Сингапуром, и anycast/GeoDNS привели его в
  `sgp`, а его данные — в `jkt`) — Gateway региона входа либо (а)
  прозрачно проксирует запрос в Gateway домашнего региона (дополнительный
  межрегиональный прыжок, приемлемый для нечастых по объёму
  запросов/разовых операций), либо (б) возвращает клиенту явное указание
  "region endpoint" домашнего региона, и клиентское приложение
  переключает последующие запросы (особенно долгоживущие — стриминг
  геолокации водителя) напрямую на домашний регион, минуя повторное
  проксирование. Второй вариант предпочтителен для сессий с высокой
  частотой запросов (например, активная поездка), первый — приемлем для
  редких/разовых операций.

### 4. Поведение при поездках рядом с границей регионов

Ключевое правило: **регион-владелец поездки фиксируется в момент создания
заказа** и равен домашнему региону пассажира (`booking_id` создаётся и живёт
целиком в этом регионе, см. [02-replication.md](02-replication.md)). Он не
меняется в течение жизни поездки, независимо от того, куда именно
перемещаются GPS-координаты водителя или пассажира во время самой поездки:

- Если водитель, назначенный на поездку, физически пересекает границу
  между зонами обслуживания регионов (например, паромный/наземный
  трансграничный маршрут), `DriverLocationUpdated` для активной поездки
  этого водителя продолжает публиковаться в Kafka-кластер региона,
  которому принадлежит поездка (региона пассажира), а не переключается на
  регион, в котором физически оказались координаты — это позволяет саге
  ([Task2/04-saga.md](../Task2/04-saga.md)) оставаться полностью в границах
  одного региона в течение всей поездки.
- Домашний регион самого водителя (для целей его профиля, заработка,
  Payouts — регуляторно значим, см. [05-compliance.md](05-compliance.md))
  не меняется из-за одной трансграничной поездки; после завершения
  поездки обычный поток данных водителя (доступность, история назначений)
  возвращается к его собственному домашнему региону через штатные,
  нерегулярные (не потоковые) каналы — глобально реплицируется не более,
  чем тонкий IAM-индекс/справочные данные (см.
  [02-replication.md](02-replication.md)), а не детальная история
  локации.
- Регулярное трансграничное обслуживание (не разовая поездка, а системная
  практика) — это бизнес/регуляторное решение (нужно ли вообще разрешать
  водителям одного региона обслуживать пассажиров другого на постоянной
  основе), а не чисто техническая задача; архитектура поддерживает разовый
  случай техническим механизмом выше, но не принимает решения о бизнес-
  политике трансграничного обслуживания.

Диаграмма: [geo-routing-schema.puml](geo-routing-schema.puml).

## Альтернативы

- **Только GeoDNS, без Anycast.** Отклонено как недостаточное: DNS-ответы
  кешируются клиентами/резолверами на время TTL — при отказе региона
  переключение трафика ждёт истечения TTL у уже закешировавших ответ
  клиентов, что не соответствует требованиям быстрого аварийного
  переключения ([04-failover.md](04-failover.md)).
- **Только Anycast, без проверки region affinity в токене.** Отклонено:
  anycast даёт лишь сетевую близость точки входа, но не решает, где лежат
  данные конкретного пользователя — без проверки `home_region` запрос
  индонезийского пользователя, попавший по anycast в Сингапур, был бы
  необработан (данные физически отсутствуют в `sgp`).
  Region affinity в токене обязателен независимо от механизма достижения
  точки входа.
- **Определение домашнего региона по текущему GPS/IP на каждый запрос,
  без фиксации в токене.** Отклонено: домашний регион — это не текущее
  местоположение, а то, где физически живут данные пользователя
  ([02-replication.md](02-replication.md)); определение по текущей
  геопозиции на каждый запрос привело бы к попыткам обратиться не в тот
  регион при каждой поездке за границу домашнего региона, а не только в
  редких пограничных случаях.
- **Полный запрет обслуживания вне домашнего региона (жёсткая блокировка
  роуминга).** Отклонено: противоречит естественному пользовательскому
  сценарию (турист/командировка); вместо запрета реализован механизм
  прозрачного проксирования/редиректа (п. 3).

## Компромиссы и риски

- Проксирование запроса в домашний регион (сценарий роуминга, вариант "а"
  в п. 3) добавляет межрегиональную задержку (потенциально сотни
  миллисекунд, см. [02-replication.md](02-replication.md)) для затронутых
  запросов — приемлемо как исключение для роуминга, но неприемлемо как
  типовой путь; корректность выбора домашнего региона при регистрации
  критична для того, чтобы это оставалось исключением.
- Клиентское переключение на прямой endpoint домашнего региона (вариант
  "б") требует поддержки такой логики в мобильных приложениях (нужно
  доработать клиентские SDK) — не бесплатно с точки зрения разработки
  клиента.
- Anycast-маршрутизация зависит от корректности BGP-анонсов и качества
  пиринга провайдера в каждом регионе — сетевые аномалии/неоптимальный
  пиринг могут в редких случаях направить клиента не в топологически
  оптимальный регион; это внешний фактор, не полностью контролируемый
  архитектурой приложения.
- Правило "регион поездки фиксируется по домашнему региону пассажира"
  означает, что водитель в приграничной зоне может обслуживать поездки,
  формально принадлежащие не его домашнему региону — это создаёт
  регуляторный вопрос (в каком регионе физически находится обработка
  данных водителя во время такой поездки), требующий согласования с
  юридической функцией отдельно от чисто технического решения (см.
  [05-compliance.md](05-compliance.md)).
