# ADR-T3-03: Механизм геомаршрутизации

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда

## Контекст

При региональном шардинге ([02-replication.md](02-replication.md)) нужно
разделить два разных понятия. Профиль пользователя, IAM-атрибуты и account
data физически хранятся в регионе профиля. Но операционная поездка должна
обрабатываться рядом с местом оказания услуги: там находятся локальная
карта, локальные водители, правила рынка, модель цены, Fraud realtime,
локальный Payments Adapter и Notification Adapter.

Поэтому нельзя маршрутизировать создание поездки только по "домашнему"
региону пассажира. Пассажир может быть зарегистрирован в Бразилии, но
заказывать такси в Индонезии; в таком случае профиль остаётся в Бразилии,
а поездка должна выполняться в регионе Индонезии.

## Требования

- Первое соединение клиента должно устанавливаться с минимальной задержкой
  — маршрутизация должна учитывать сетевую близость, а не только
  DNS-геолокацию по IP.
- Нужно явно различать:
  - `profile_region` — регион хранения профиля, IAM-атрибутов и account data;
  - `ride_region` — регион выполнения конкретной поездки;
  - `tenant_region` — разрешённый регион партнёра/рынка, если применимо;
  - `current_edge_region` — ближайшая edge-точка/API Gateway, куда пришёл запрос.
- `profile_region` может быть claim токена и заменяет прежнее
  неоднозначное использование `home_region`. Если старый claim
  `home_region` остаётся на переходный период, он трактуется только как
  alias `profile_region`, а не как регион поездки.
- `ride_region` определяется по точке посадки, выбранному городу,
  tenant/market, локальному домену или конфигурации приложения.
- Операционные сервисы поездки работают в `ride_region`: Booking, Driver,
  Pricing, Geography, Fraud realtime, локальный Payments Adapter и
  Notification Adapter.
- Profile/Identity может оставаться в `profile_region`; hot path поездки
  не должен выполнять прямое межрегиональное обращение к пользовательской
  БД на каждый location update или шаг Saga.
- После определения `ride_region` активная поездка закрепляется за ним до
  завершения, кроме контролируемого disaster recovery
  ([04-failover.md](04-failover.md)).
- Поездка рядом с границей регионов не должна требовать синхронной
  межрегиональной координации в процессе выполнения.

## Решение

### 1. GeoDNS + Anycast выбирают current_edge_region

DNS-имя API Gateway резолвится в адрес ближайшего по сети региона:
GeoDNS определяет исходный регион клиента по IP, а latency-based routing
уточняет выбор по фактически измеренной задержке. Anycast IP API Gateway
анонсируется из всех регионов; сеть приводит клиента в топологически
ближайший здоровый edge.

Результат этого шага — только `current_edge_region`: ближайшая точка входа.
Он не является ни `profile_region`, ни `ride_region` и не решает, где будет
создана поездка.

Для соответствия целям [04-failover.md](04-failover.md) входной слой
работает как GSLB/DNS + Anycast:

- health checks проверяют не только alive Gateway, но и готовность региона
  принимать Tier-1 ride APIs: Gateway capacity, Kubernetes endpoints,
  PostgreSQL writer health, Kafka ISR и базовые synthetic checks
  `CreateBooking`/`DriverReservation`;
- DNS TTL для Tier-1 endpoints — 30–60 секунд;
- перед выводом endpoint из ротации применяется connection draining, чтобы
  не обрывать уже принятые запросы без необходимости;
- неисправный регион исключается из GSLB/Anycast routing автоматически,
  но возврат после регионального инцидента требует cooldown/hold-down и
  подтверждения SRE, чтобы защититься от flapping;
- исключение региона из edge routing не меняет `ride_region` уже созданной
  поездки: перенос активной поездки допустим только по DR-процедуре.

### 2. profile_region отвечает за профиль, а не за поездку

При регистрации/первой аутентификации пользователю назначается
`profile_region` — регион, где живут профиль, IAM-атрибуты, настройки
аккаунта и допустимые account data. Identity Service включает это значение
в токен как claim `profile_region`. Старый claim `home_region`, если
остаётся для совместимости клиентов, является только alias
`profile_region`.

Profile/Identity-запросы, управление аккаунтом, удаление профиля и
изменение IAM-атрибутов маршрутизируются в `profile_region`. Операционная
поездка не обязана идти туда.

### 3. ride_region определяется для конкретной операции CreateBooking

Для `CreateBooking` API Gateway или выделенный routing policy компонент
определяет `ride_region` по приоритету:

1. **Точка посадки**: GPS pickup или geocoded pickup address попадает в
   полигон обслуживаемого города/рынка.
2. **Выбранный город**: если пользователь явно выбрал город в приложении,
   этот выбор используется как сильный сигнал, пока он разрешён tenant и
   market policy.
3. **Tenant/market**: `tenant_id` и конфигурация партнёра ограничивают
   набор допустимых регионов и рынков (`tenant_region`).
4. **Локальный домен или конфигурация приложения**: региональный endpoint,
   брендированный домен партнёра или market config приложения могут
   ограничить выбор, но не заменяют проверку pickup/city.

Если `current_edge_region` не равен вычисленному `ride_region`, Gateway
либо прозрачно проксирует `CreateBooking` в Gateway региона поездки, либо
возвращает клиенту endpoint `ride_region`, чтобы дальнейшая активная
сессия шла напрямую туда. Для частых location updates прямой endpoint
`ride_region` обязателен: нельзя обращаться в БД профиля другого региона
на каждый update.

### 4. Операционный контур поездки работает в ride_region

После вычисления `ride_region` Booking Service создаёт `booking_id` и Saga
в этом регионе. До завершения поездки `ride_region` фиксируется в записи
Booking и в событиях Kafka. В `ride_region` работают:

- Booking Service и Booking Saga Orchestrator;
- Driver Service и выбор локальных водителей;
- Pricing Service и локальная модель цены/локальные тарифы;
- Geography Service и локальная карта/геозоны;
- Fraud realtime для оперативной проверки заказа;
- локальный Payments Adapter, разрешённый для рынка поездки;
- локальный Notification Adapter для доставки через допустимых провайдеров.

Profile/Identity остаётся в `profile_region`. Чтобы не тянуть профиль по
межрегиональной сети на каждом шаге, `ride_region` использует только
разрешённые минимальные данные:

- claims токена: `user_id`, `tenant_id`, `profile_region`, роли,
  verified flags, market eligibility;
- локальную read-only проекцию минимальных profile attributes;
- кэш без чувствительных данных и без платёжных реквизитов;
- асинхронную репликацию разрешённых данных по allowlist.

Прямое чтение пользовательской БД `profile_region` из Driver/Pricing/
Geography на каждом location update запрещено. Если нужного атрибута нет
в токене или локальной projection, операция должна деградировать
контролируемо или запросить явное обновление eligibility через
асинхронный процесс, а не делать синхронный cross-region call в hot path.

### 5. Сценарий: Бразилия → Индонезия

Пользователь зарегистрирован в Бразилии:

- `profile_region = sao`: профиль, IAM-атрибуты, настройки аккаунта и
  account data остаются в Сан-Паулу.
- Пользователь прилетает в Индонезию и выбирает pickup в Джакарте.
- Ближайший edge может быть `jkt` или `sgp`, но routing policy определяет
  `ride_region = jkt` по точке посадки, выбранному городу и market policy.
- Booking создаётся в `jkt`; Saga, Kafka-топики поездки и операционные
  записи находятся в `jkt`.
- Geography использует локальную индонезийскую карту и зоны.
- Pricing использует локальную модель цены, локальные тарифы и surge для
  `jkt`.
- Driver выбирает локальных водителей из пула `jkt`.
- Payments использует допустимый локальный Payments Adapter для Индонезии
  с токенизированным способом оплаты; при необходимости eligibility
  платёжного метода проверяется через локальную projection/allowlist, а не
  прямым чтением БД профиля `sao` на каждом шаге.

Такой сценарий не отправляет операционный заказ в Бразилию только потому,
что профиль пассажира хранится в `sao`.

### 6. Пограничные случаи

| Случай | Поведение |
|---|---|
| GPS недоступен | Клиент должен выбрать город или адрес посадки вручную. До определения pickup/city создаётся только предзапрос без `booking_id`; полноценный `CreateBooking` не стартует. |
| Координаты около границы | Используется polygon lookup с hysteresis/геозоной допуска. Если pickup попадает в спорную область, применяется выбранный город или market policy; после создания заказа `ride_region` фиксируется до завершения. |
| Несовпадение market в токене и координат | Gateway проверяет `tenant_id`, `tenant_region`, eligibility и координаты. Если tenant не имеет права обслуживать рынок pickup, заказ отклоняется или пользователю предлагается переключить market/город. Нельзя молча маршрутизировать заказ в `profile_region`. |
| Пользователь выбирает город вручную | Ручной выбор города используется как вход в определение `ride_region`, но валидируется по pickup/address и tenant/market policy. При конфликте приложение просит подтвердить город или исправить точку посадки. |
| Долгоживущая активная поездка | Клиент и водитель используют endpoint `ride_region`; location updates, Saga events и Driver/Pricing/Geography остаются локальными для региона поездки. |
| Disaster recovery | Перенос активной поездки в другой регион допускается только по процедуре DR из [04-failover.md](04-failover.md), с юридическим и операционным подтверждением, если затронута data residency. |

Диаграмма: [geo-routing-schema.puml](geo-routing-schema.puml).

## Альтернативы

- **Маршрутизировать операционную поездку по `profile_region`/старому
  `home_region`.** Отклонено: международный путешественник отправил бы
  заказ в регион профиля, где нет локальной карты, локальных водителей,
  локальной модели цены и допустимого платёжного адаптера для места
  оказания услуги.
- **Только GeoDNS/Anycast без вычисления `ride_region`.** Отклонено:
  edge-близость ускоряет вход, но не гарантирует, что запрос попал в
  регион рынка поездки; мобильный NAT или сетевой пиринг могут привести
  пользователя в соседний регион.
- **Определять `ride_region` по текущему GPS на каждый запрос.**
  Отклонено: активная поездка должна быть закреплена за регионом создания
  до завершения, иначе пересечение границы или GPS-jitter приведут к
  расщеплению Saga, Kafka-событий и Driver state между регионами.
- **Полная глобальная репликация профилей для роуминга.** Отклонено как
  базовая модель: увеличивает blast radius утечки и требует юридической
  квалификации cross-border transfer для каждого рынка. Для hot path
  достаточно token claims, read-only projection, кэша без чувствительных
  данных и разрешённой асинхронной репликации.

## Компромиссы и риски

- Первый запрос путешественника может попасть в `current_edge_region`,
  отличный от `ride_region`, и получить один дополнительный hop или
  redirect. После определения `ride_region` активная сессия должна идти
  напрямую в регион поездки.
- Локальная projection минимальных profile attributes требует строгого
  allowlist и TTL. Ошибка классификации поля может нарушить принятую
  residency/cross-border policy, поэтому схема projection должна проходить
  комплаенс-ревью и при необходимости подтверждение local legal counsel
  вместе со схемами событий ([05-compliance.md](05-compliance.md)).
- Не все способы оплаты профиля могут быть доступны в регионе поездки.
  Payments Adapter в `ride_region` должен явно проверять допустимость
  токена/провайдера для market, а не предполагать, что любой payment method
  из `profile_region` пригоден локально.
- Водители и пассажиры с разными `profile_region` могут участвовать в
  одной поездке. Операционные данные поездки принадлежат `ride_region`, а
  профильные и IAM-данные каждого участника остаются в их
  `profile_region`.

## Статус

Предложено.
