# ADR-T3-06: Обоснование механизмов защиты

Дата: 2026-07-17
Авторы: Архитектурный комитет GoFuture, платформенная команда, SRE

## Контекст

С глобальным развёртыванием в 4 регионах ([01-region-selection.md](01-region-selection.md)),
публичным API для мобильных приложений и веб-портала
([Task1/02-service-map.md](../Task1/02-service-map.md)), межсервисным
взаимодействием поверх Kafka/gRPC ([Task2/01-domain-events.md](../Task2/01-domain-events.md))
и растущим числом локальных интеграций и секретов
([05-compliance.md](05-compliance.md)) периметр и внутренняя защита
платформы нуждаются в явном наборе механизмов, показанных на
[c2-to-be-security.puml](c2-to-be-security.puml) — доработке
[Task1/c2-to-be.puml](../Task1/c2-to-be.puml). Этот документ объясняет,
почему выбран именно такой набор.

## Требования

- mTLS между всеми доменными и платформенными сервисами уже мандирован
  требованием Б1 ([Task1/01-nfr.md](../Task1/01-nfr.md)) — нужен
  инфраструктурный механизм, который делает это гарантией платформы, а не
  практикой, зависящей от дисциплины каждой команды.
- Публичная точка входа (API Gateway) обслуживает мобильные приложения по
  всему миру при заявленном масштабе 500 тыс. конкурентных поездок
  (требование П1, [Task1/01-nfr.md](../Task1/01-nfr.md)) — представляет
  ценную цель для атак уровня приложения и объёмных атак.
- Секреты (креды БД на регион, ключи локальных платёжных провайдеров,
  сертификаты, см. [05-compliance.md](05-compliance.md)) не должны
  храниться в конфигурации/переменных окружения в открытом виде.
- Сетевая сегментация должна ограничивать последствия компрометации
  одного сервиса, дополняя логическую изоляцию Database-per-Service
  (требование Б4, [Task1/01-nfr.md](../Task1/01-nfr.md)).

## Решение

На [c2-to-be-security.puml](c2-to-be-security.puml) добавлены пять новых
элементов (выделены красным, легенда "красное = новые/изменённые элементы
относительно [Task1/c2-to-be.puml](../Task1/c2-to-be.puml)"):

### WAF перед API Gateway

Единственная публичная точка входа платформы
([Task1/02-service-map.md](../Task1/02-service-map.md)) подвержена типовым
атакам уровня приложения — SQL/NoSQL-инъекции, credential stuffing на
эндпоинты Identity Service, злоупотребление API. WAF фильтрует такие
паттерны на уровне HTTP до того, как запрос достигнет Gateway или
доменных сервисов — снижает нагрузку на Identity Service по отражению
атак на аутентификацию, не полагаясь только на бизнес-логику
rate-limiting внутри сервисов.

### DDoS-защита перед WAF

Публичный сервис такси-агрегатора с мобильными клиентами по всему миру —
типичная цель объёмных атак. Anycast для API Gateway
([Task3/03-geo-routing.md](03-geo-routing.md)) распределяет легитимную
нагрузку по регионам, но сам по себе не является защитой от
целенаправленной объёмной атаки — она может насытить канал/протокольный
стек до того, как трафик дойдёт до уровня приложения. Размещена перед
WAF: объёмный "мусорный" трафик должен отсекаться раньше, чем он достигнет
вычислительно более дорогого слоя разбора правил WAF.

### Network Security Groups / Firewall

Дополняет логическую изоляцию Database-per-Service (Б4,
[Task1/01-nfr.md](../Task1/01-nfr.md)) сетевым уровнем: даже если один
сервис скомпрометирован на уровне приложения, сетевые правила
ограничивают, к каким БД/сервисам он вообще способен обратиться на уровне
сети, — вторая независимая линия обороны, не полагающаяся только на
корректность аутентификации/авторизации внутри сервиса.

### Service Mesh (control plane) — mTLS между сервисами

Требование Б1 ([Task1/01-nfr.md](../Task1/01-nfr.md)) существовало и
раньше; на [Task1/c2-to-be.puml](../Task1/c2-to-be.puml) mTLS уже был
указан на части связей (Gateway↔ACL, ACL↔сервисы), но не был выведен как
явная инфраструктура и не покрывал все синхронные вызовы — на
[c2-to-be-security.puml](c2-to-be-security.puml) связи `Booking → Pricing`
и `Booking → Driver Service` тоже обновлены с явной пометкой mTLS. Service
Mesh централизует выпуск и ротацию сертификатов для всех сервисов
(показано связями "Выпуск/ротация сертификатов mTLS") — без единой
инфраструктуры это стало бы обязанностью каждой доменной команды
реализовывать и поддерживать самостоятельно, с риском расхождения
практик и постепенной эрозии требования Б1 со временем.

### Secrets Manager

Число секретов растёт с числом регионов и локальных интеграций: креды БД
на каждый из 4 регионов ([01-region-selection.md](01-region-selection.md)),
ключи локальных платёжных провайдеров ([05-compliance.md](05-compliance.md)),
корневые сертификаты Service Mesh. Централизованное безопасное хранение с
ротацией убирает секреты из конфигурации/переменных окружения и создаёt
единую точку аудита обращений к ним — согласуется с требованием аудита
доступа ([05-compliance.md](05-compliance.md)).

## Альтернативы

- **mTLS на уровне библиотек в каждом сервисе, без выделенного Service
  Mesh.** Отклонено: несогласованная реализация в разных доменных
  командах, отсутствие центральной точки ротации сертификатов и аудита
  межсервисного трафика — риск постепенной деградации требования Б1 по
  мере роста числа сервисов и команд.
- **Секреты в зашифрованных переменных окружения деплоя без выделенного
  Secrets Manager.** Отклонено: ротация секрета требует передеплоя
  сервиса вместо динамического обновления; нет единого журнала обращений
  к секретам для аудита.
- **Объединить WAF и DDoS-защиту в один компонент диаграммы.** Отклонено
  как чрезмерное упрощение: это разные технические функции (сетевой
  уровень против уровня HTTP-семантики), и конкретная реализация каждой
  может отличаться по регионам в зависимости от облачного провайдера
  (провайдер `jkt`/`sao` может отличаться от провайдера `core`, см.
  [01-region-selection.md](01-region-selection.md)) — раздельное
  отображение точнее и не привязывает решение к одному вендору.

## Компромиссы и риски

- WAF и DDoS-защита добавляют задержку на пути запроса и риск ложных
  срабатываний (блокировка легитимного мобильного трафика) — правила
  должны быть настроены под специфику трафика GoFuture и отслеживаться
  через существующий мониторинг ([Task2/06-monitoring.md](../Task2/06-monitoring.md)).
- Service Mesh добавляет sidecar-прокси к каждому сервису — дополнительные
  вычислительные расходы и ещё один компонент в эксплуатации SRE,
  аналогично тому, как ACL/feature-флаги ранее были отмечены как временная
  нагрузка ([Task1/04-backward-compatibility.md](../Task1/04-backward-compatibility.md));
  здесь нагрузка постоянная, но обоснованная прямым требованием Б1.
- Secrets Manager становится критичной зависимостью — его недоступность
  при старте сервиса блокирует получение секретов; требует собственного
  уровня доступности не ниже Tier 1 (Д3, [Task1/01-nfr.md](../Task1/01-nfr.md)).
- Network Security Groups при неверной настройке создают ложное чувство
  защищённости — это дополнительный, а не единственный уровень защиты;
  аутентификация и авторизация на уровне приложения (Б2,
  [Task1/01-nfr.md](../Task1/01-nfr.md)) остаются обязательными
  независимо от сетевых правил.

## Статус
